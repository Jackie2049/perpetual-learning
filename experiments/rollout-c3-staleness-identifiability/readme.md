# C3 成对报值（η／S）的可执行性：约定能分辨什么、不能分辨什么

2026-11-02，M1。支撑 [rollout 调研主文档 §21.7](../../notebook/rollout-performance-research.md)，
接 §21.6 的结论"四个框架都没有按 C3 字面定义报 η，全是近似"。

**不是 GPU 实测，不是任何系统的端到端**。进程内事件图仿真，只用标准库，墙钟是任意虚拟秒。

## 一句话结论

**C3 要"成对报 η 与 S"，本实验证明的是这两项各自能分开什么、又分不开什么。**
用三种近似 η 都能判"某个配置比同步配置更陈旧"，但其中一种（只看引擎侧装载版本）**恒报 0**，
在生产数据上会得出"没有陈旧"这一反方向的结论；
单独报 S 时，**四个配置的 S 完全相同（23.97）而 η 上限分别是 0／7／19**——
只报 S 的这一栏，读不出它们之间的任何区别。最后，弹性窗口的"η=0"只在
FIFO 重放 + 窗口不淘汰旧组 + 队列无积压这三条同时成立时为真，改任一条都会破坏它，
而**只看最大值会把"窗口满"与"积压满"读成同一个数**。

## 为什么做

§21.3（P-5）把 C3 写成报值约定：async 下必须成对报 η 分布与 S，并规定同步化基准取同栈 η=0 整步墙钟。
§21.6 已核出**语料里没有人按这个定义报**（SkyRL 是步数年龄、NeMo 是按组淘汰、veRL 是版本标签或计数阈值、OpenRLHF 无逐条版本），
但没回答两件事：**用这些近似，C3 自己想做的判断还做不做得对**；以及**"η=0"这个基线什么时候才是真 0**。
而 §21.3 在"同步化时间基准"一条里已经写下了"弹性窗口不建 L5"这类设定下的隐含假设，却从未验证过它成立的条件。

## 模型

时间单位：一个训练步。归一化到生成周期 `T = 1.0`；`sync_extra = 0.20` 是"同步配置里更新不重叠时多出来的一段"。

| 配置 | 引擎／训练关系 | 用途 |
|---|---|---|
| `sync` | 生成完一批才更新；整步墙钟 = T + 0.20 | η=0 参照（真正的同步） |
| `sync-pipelined` | 引擎不等训练结束就开下一批；整步墙钟 = T；消费的仍是本轮最新批 | **η=0 的另一种同步形态**——Q2 里"同 S 不同 η"的对照组 |
| `async-stale` | 引擎快 1.5 倍、策略滞后 1 代、陈旧窗口 8 | Q1 的中度陈旧 |
| `async-deep` | 引擎快 2.5 倍、策略滞后 3 代、陈旧窗口 20 | Q1 的重度陈旧 |
| `async-starved` | 引擎比训练慢一倍，训练侧一半时间在等 | Q2 的分母错（空转） |

每批 `N_GROUPS=8` 组 × `N_SAMPLES=4` 条；组整体失败（概率 0.25）则整组丢弃。
**真值 η = 消费时的训练版本 − 生成该批时用的权重代**；队列按 FIFO（或对照组 LIFO）取批，超过陈旧窗口的组被淘汰。

**可观测性纪律**：三种近似 η 与两种 S 读法都只吃引擎侧真能看见的东西
（它自己产出的批、这批用的权重代、是否因为攒不够一批而空转），真值另走仿真内部；
`engine_view()` 把空转步从"引擎可见"里剔除，这条由 `test_engine_view_drops_idle_rows` 守着。

## 三种近似 η（对应 §21.6 核过的四框架）

| 键 | 怎么算 | 对应 |
|---|---|---|
| `trainer_step` | 消费训练版本 − 生成时版本 | veRL 按步标签（在本模型里恰好等于真值） |
| `engine_weight` | 只看这批内部用了几代权重（引擎不知训练侧推进到哪） | SkyRL 式"只看已装载版本" |
| `max_only` | 整段 trace 只给一个标量：最大年龄 | NeMo 式按版本淘汰（无分布） |

## 结果

### Q1：近似 η 分得开"更陈旧"，但分不开"陈旧多少"，有一种会反向

30 种子，判据命中数：

| 判断 | 真值 | `trainer_step` | `max_only` | `engine_weight` |
|---|---|---|---|---|
| stale／deep 比 sync 陈旧 | 30/30 | 30/30 | 30/30 | **0/30** |
| deep 比 stale 更陈旧 | 30/30 | 30/30 | 30/30 | **0/30** |

- **`engine_weight` 恒报 0**：引擎看不到训练侧推进到哪一代，只能报本批内部的代差，于是年龄被压成 0。
  这在**生产数据上最危险**——它不是"读数偏低"，而是把"有陈旧"读成"没陈旧"，方向上正好相反。
  §21.6 把这种近似记作"部分可得"，本实验补上了它的失效方式：**能识别、不能定级**。
- **`max_only` 在"谁更陈旧"上够用，在"陈旧多少"上结构性失效**：它只有一个数，P50／P90 不存在
  （`test_max_only_cannot_report_distribution` 守着）。而本模型的真值分布确实有宽度
  （`async-deep` 的 η 在 1–19 之间，`test_eta_distribution_is_not_degenerate`），
  所以"只报 max"不是无害的简化。

### Q2：单独报 S 时，四个配置不可区分

| 配置 | S（C3 口径） | η 上限 | 分子换成生成量后的高报 | 分母换成活跃步后 |
|---|---|---|---|---|
| `sync` | 19.98 | 0 | 1.335× | 1.000× |
| `sync-pipelined` | 23.97 | **0** | 1.335× | 0.833× |
| `async-stale` | 23.97 | **7** | 1.335× | 0.833× |
| `async-deep` | 23.97 | **19** | 1.335× | 0.833× |
| `async-starved` | 11.93 | 1 | 1.342× | **1.667×** |

- **三个配置的 S 逐位相同（相对差 0.0%）、η 上限差 19**——这正是 C3"必须成对报"的机制证据：
  S 的提升在这里**一条轨迹都多不起来**，它全部来自"更新不再串行等待"，与生成侧产出无关。
- **分子错**：换成生成侧计数后高报恰好等于 `1/(1−丢弃率)`（逐种子恒等，测试守着）；
  本模型丢弃率 25.09%，故高报 1.335×。§21.6 用 SkyRL 每步丢 8/32 组估到 33.3%，量级一致、口径自洽。
- **分母错**：把空转剔掉后，`async-starved` 从 11.93 变 20.03（×1.667 = 1/(1−0.5)/(1.2)），
  而没有空转的配置反而下修到 ×0.833——因为活跃步的分母多摊了一段 `sync_extra`。
  **两类偏差方向相反，只看"偏高还是偏低"分不清是哪一类**。

### Q3：换基线叙事，方向会反

同一底层真值，"async 相对基线快多少"的三种报法：

| 配置 | 诚实口径（接纳量、sync 基线） | 分子换成生成量 | 基线换成 `async-stale` |
|---|---|---|---|
| `sync-pipelined` | 1.200 | 1.200 | 1.000 |
| `async-stale` | 1.200 | 1.200 | 1.000 |
| `sync` | 1.000 | 1.000 | **0.833（30/30 种子读成"更慢"）** |

- 本模型里丢弃率与配置无关，所以**分子错只改幅度不改方向**（`test_honest_and_generated_agree_on_direction` 显式固定这一前提）。
  真实系统里丢弃率与丢弃机制相关（DAPO 组过滤、陈旧淘汰），此时分子错会变成方向错——这一点本实验**没有**证明，只标出机制差异。
- **基线换错则 30/30 种子全部读反**：把另一个异步配置当"同步基线"，会让真正的同步配置看起来比基线慢。
  这正是 §21.3 第 3 条"没有 η=0 同栈参照时只能报方向、不得报倍数"要防的错——本实验给出它的量化代价。

### Q4：弹性窗口里的"η=0"成立条件

FIFO 与 LIFO 两臂作对照（两臂读数相同 ⇒ 该档下重放顺序不起作用，读数只反映积压与窗口）：

| 档 | FIFO η 上限 | LIFO η 上限 | FIFO 空转率 | 顺序起作用 |
|---|---|---|---|---|
| 引擎与训练同速、窗口 8 | 1 | 1 | 0 | 否 |
| 引擎快 2 倍、窗口 8 | **7** | 1 | 0 | 是 |
| 引擎快 2 倍、窗口 32 | **31** | 1 | 0 | 是 |
| 引擎快 5 倍、窗口 32 | **31** | 1 | 0 | 是 |
| 引擎快 2 倍、窗口 0 | 0 | 0 | **1.00** | 否 |
| 引擎比训练慢、窗口 8 | 1 | 1 | 0.50 | 否 |

- **只是 FIFO 并不产生 η=0**：引擎一快、旧组就压在队列里被 FIFO 消费，η 反而最大（7–31）。
- **窗口收到 0 才给出 η=0，但代价是全部空转**：这时的 0 是"不消费任何旧组"换来的，不是免费的。
- **只报 max 会把两种完全不同的情形读成同一个数**：`rate2_window32` 与 `rate5_window32` 的 FIFO max 都是 31
  （被窗口顶住），但均值 28.82 vs 30.50、积压深度差一倍。
  **这就是 §21.3 要求报分布而不是单值的实证理由**。

## 这次自查修正了什么

本实验改过九处，全部是**先跑出数、回头才发现口径不对**，按发生顺序记：

1. **同步配置的 η 不为 0**：初版让同步模式也走"滞后一代"的生成路径，η 恒为 1，Q1 的"比 sync 更陈旧"判据等于零敏感。
2. **`engine_weight` 读法恒 0 却当成了"精确"**：初版把它算成"真值"，于是三种近似都对；改成只吃引擎可见量后才是本报告里的失效形态。
3. **`max_only` 只是真值的换皮**：初版按步取 max 再求分布，与真值完全相同（0.0 偏差），说明它根本没模拟"只报一个数"。
4. **丢弃率与 η 同源**：初版队列既决定陈旧又决定丢弃，导致 `async-starved` 的 S 与其它配置全部相同、Q2 无对照组。
5. **空转被写成"空批步骤"**：初版把"攒不够一批"记成一步（`n_gen=0`），分母错与弹性窗口的空转率永远量到 0。
6. **ε 混进模拟读数**：某一版让 async 根据假设的 ε 调整墙钟，等于**用结论证明结论**（速度比当然等于公式），已全部撤掉。
7. **`gennum_ratio` 的恒等式写成了跨种子均值式**：`1/(1−丢弃率)` 只逐种子成立，用均值之比会差 2e-4。
8. **活跃步分母的推导错了两版**：正确的比例是 `1/(1−空转率)/(1+sync_extra/T)`，我先后写成 `1/(1−空转率)` 与 `(1−空转率)/(1+extra)`。
9. **弹性窗口的对照一度"判别力为零"**：早先几档 FIFO／LIFO 读数完全相同，被当成"顺序不重要"写进结论；
   改为扫描积压深度 × 窗口后才发现顺序确实起作用，同时发现"max 被窗口顶住"这一新读数。

其中 1、2、3、5、7、8 由单元测试抓出；4、6、9 由人工核对数值关系发现——第 6 条最严重：
它会让"约定可执行"这个结论在没有证据的情况下自己成立。

## 边界（引用时必须一并写）

- **进程内事件图仿真**，没有 GPU、没有真实引擎、没有 Ray／vLLM／FSDP；墙钟为任意虚拟秒，
  **不可与任何论文报值相除**（§19.1 规则一）。
- 四个配置是**构造出来的**，代表"滞后深度／积压深度／窗口"的几种形态，不是任何具体系统的画像；
  `T=1`、`N_GROUPS=8`、失败率 0.25 都是构造参数。
- **本实验不支持"某框架报错了 η／S"**，只支持"用 §21.6 核过的那几类近似，C3 的哪一半判断还成立、哪一半不成立"。
- Q3 的"分子错不改方向"依赖本模型"丢弃率与配置无关"这一前提，真实系统里不成立，正文已注明。
- 三种近似的对应关系是**按语义构造**的，不是从框架源码逐行移植；它与 §21.6 的源码核验互为参照，不能替代后者。
