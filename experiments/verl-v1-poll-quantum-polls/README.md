# 采样轮询量子不是"每步固定扣 2s"，而是**释放时刻被量化到轮询网格**——并用一个计数器为下一次窗口补上机制读数

2026-11-05 执行（M5 算力侧，TM-008 机制补强；无卡轮）。此前结论见 [2 卡 sync](../verl-v1-poll-quantum/README.md)、[DAPO](../verl-v1-poll-quantum-dapo/README.md)、[4 卡](../verl-v1-poll-quantum-dapo-g4/README.md)、[colocate_async](../verl-v1-poll-quantum-async/README.md)、[stale](../verl-v1-poll-quantum-stale/README.md)、[separate_async](../verl-v1-poll-quantum-separate/README.md)／[rollout-bound](../verl-v1-poll-quantum-separate-bound/README.md)。机制背景 §13.44、§13.49。

> **一眼结论。** ① 每步 `timing_s/gen` 在 P=2.0 下落在 **2.0 网格 + 常数偏移 c** 上，不是连续量：2 卡固定批两簇 2.1575／4.1717（**间隔 2.0142**，簇内散度 0.0115／0.0294），P=0.5 两簇 2.1621／2.6606（**间隔 0.4985**）；五个簇跨三个独立臂给出 **c = 0.1625 ± 0.0048 s**。② 因此"等待"= `ceil(D/P)·P − D`，**是对 P 的锯齿**；归档里的"斜率 0.98（2 卡 DAPO）／0.59（4 卡 DAPO）"是这条锯齿在 [0.1, P] 上的**割线**，取值由该配置的 D 落在格子里的位置决定，不是另一个机制。③ 单轮公式**不适用于 DAPO 臂**（0–4/12 步命中），因为一个训练步里有多次派发轮次——这正是本轮补的计数器要量的东西。**零 GPU 读数；纯归档重算 + CPU 驱动的真实源码。**

## 一、要回答的问题

§13.49 把 4 卡 DAPO 的等待拆成"固定等待"后给出 **每步平均等待 ≈ 0.59 × poll_interval**，并记录 2 卡同模型是 **0.98**，结论写成"等待量随配置变，不能当常量迁移"。这句话描述了现象，但没解释**为什么**斜率会变，也没给出可预测形式；TM-008 对外写作时只能写成"0.03–0.06 s 量级的方向性收益"。

本轮要问的是：**这个斜率差异是机制不同，还是同一个机制的相位不同？**

## 二、模型

`ReplayBuffer.sample()` 的结构（真实源码 `verl/trainer/ppo/v1/replay_buffer.py`）：先同步元数据、判够不够；不够就 `time.sleep(poll_interval)` 再回读。所以训练步被释放的时刻是**第一个越过"批次已终结"的轮询点**：

```
gen_i(P) = ceil(D_i / P) * P + c
```

- `D_i`：本步自己的生成耗时（不含轮询等待）；
- `c`：计时块内最后一个 sleep 之后的工作（元数据回读、选择、materialise、计时边界）。

这个模型只说**何时被释放**，不说 GPU 快慢。它有一个可证伪的硬签名：**P=2.0 时取值只能落在 `k·2.0 + c` 上，不能连续**。

## 三、读数一：量化签名（不做配对、不拟合斜率）

稳态 steps 3–14，按 0.1 s 容差聚类（[读数](raw/quantization.json)）：

| 臂 | 簇均值（n） | 簇内散度 | 相邻簇间隔 | 相对 `k·P` 的偏移 |
|---|---|---|---|---|
| 2 卡固定批 P=2.0 | 2.1575（6）／4.1717（6） | 0.0115／0.0294 | **2.0142** | 0.1575／0.1717 |
| 2 卡固定批 P=0.5 | 2.1621（7）／2.6606（5） | 0.0498／0.0272 | **0.4985** | 0.1621／0.1606 |
| 4 卡固定批 P=2.0 | 2.1607（12） | 0.0264 | —（单簇） | 0.1607 |

- 两个不同量子（2.0 与 0.5）各自给出与量子相等的簇间隔（2.014／0.499），**同一批运行**；簇内散度 0.01–0.05 s，是 2.0 s 的 0.5–2.5%。
- 五个簇、三个独立臂给出**同一个常数偏移 c = 0.1625 ± 0.0048 s**（0.1575／0.1717／0.1621／0.1606／0.1607）。这个数以前没被单独记过：`timing_s/gen` 里有 **约 0.16 s 不属于任何一次 sleep**。

## 四、读数二：用 P=0.1 臂做逐步预测（含负向对照）

同一配置的 P=0.1 臂给出 `D_i`（`gen_i(0.1)` 已含 ≤0.1 s 的等待与同一个 c，误差并入残差）。把它代进 P=2.0 的格子，就是**逐步预测**——只在两次运行看到同一 workload、同一顺序时成立（固定批臂：每步一次派发、同 seed）。

| 臂 | 命中（\|残差−c\| ≤0.25 s） | 备注 |
|---|---|---|
| 4 卡固定批 | **12/12**（最大偏差 0.021，sd 0.0083） | D 稳定在 1.68–1.79，全部落在同一格 |
| 2 卡固定批 | **9/12**（残差 +0.15–+0.18） | 3 步在边界上翻格，见下 |

**负向对照（在 2 卡臂上做，因为它有方差）**：

| 变体 | 命中 ≤0.25 s | 与真配对比较 |
|---|---|---|
| 真格子 P=2.0 | 9/12 | — |
| 错格子 P=1.0 | **0/12** | 全退化 |
| 错格子 P=0.5 | **0/12** | 全退化 |
| 错格子 P=3.0 | **0/12** | 全退化 |
| 打乱 D 与 step 的配对（500 次） | 中位 **7/12**（最小 5） | 退化但不像错格子那样彻底 |

打乱配对的退化幅度不大，是因为 2 卡臂的 D 本身分布窄（1.78–2.42），多数 D 的格子预测相同——这同时说明"9/12"这条读数的**信息量有限**，真正强的是读数一的簇结构（间隔等于量子、簇内 0.01–0.03 s）。

**3 个边界步是怎么回事。** steps 7／8／10 的 P=0.1 腿 D = 2.42／2.28／2.40（>2.0），按模型应翻到 4.0 格，但 P=2.0 腿实测 2.16（= 2.0 格）。合理解释是**跨运行 workload 抖动**：2 卡上这三步的生成时长在两次运行里差 0.3 s 量级，D 恰好压在 2.0 边界上，于是整格翻转。这不是模型错，是"用另一次运行测 D"的分辨力上限——也正好说明为什么该配置的斜率达到 0.98：D 就停在 2.0 附近，一半的步多付一个完整量子。

## 五、读数三：DAPO 臂不服从单轮公式（负结论，且是预期内的）

| 臂 | 命中 ≤0.25 s | 中位偏移 c | 残差 sd |
|---|---|---|---|
| 2 卡 DAPO inflight=1 | 0/12 | −0.35 | 1.79 |
| 2 卡 DAPO inflight=2 | 4/12 | +0.56 | 1.95 |
| 4 卡 DAPO inflight=2 | 0/12 | −0.43 | 1.78 |

一个训练步里有**多次派发轮次**（DAPO 过滤逐出后按 `2k` 补发，受 `max_inflight_gen_batches` 限流），每轮各自被量化一次，所以总量是若干锯齿之和，单轮公式必然对不上。这与读数是自洽的：固定批臂的斜率 0.21（4 卡，D 在格子中部）／0.51（2 卡，D 在边界），DAPO 臂 0.59／0.98——**同一机制，不同相位与轮数**。

## 六、为下一次窗口准备的计数器（本轮的可执行产物）

既然机制依赖"每步阻塞了几次轮询"，而归档里只有总时长，就没有办法把"轮数"和"每次的残余相位"分开。`poll-count.patch`（2 文件，+9 行）补上这个量：

- `_wait_for_next_poll` 计数，`sample()`／`wait_for_sampleable()` 入口清零、出口写 `{prefix}/sampler/blocking_polls`；
- `MetricsAggregator` 的 `sum` 规则登记该键（`parameter_sync_step>1` 时按迭代求和；本系列 sync／colocate_async 的 `v1.*` 配置块为空、`parameter_sync_step` 取默认 1，一步一次 `sample()`，该读数即每步值）。

**验证（CPU，真实源码执行）**：[sim-loop.py](sim-loop.py) 从树里取出 `ReplayBuffer` 类源码原样 `exec`，只把数据层（`transfer_queue`）、时钟和 `KVBatchMeta` 换成桩，用虚拟时钟驱动真实 `sample()` 循环并数 sleep：

- 打补丁树 **9/9**、未打补丁树 **9/9**（负向对照：未打补丁时该键必须不存在）；
- 结构自检包括：预填满 → 0 次轮询；到达在第一个量子内 → 1 次；到达 +5.0 s、P=2.0 → 3 次；DAPO 补发 → 每步 >1 次；P=0.1 ≥ P=2.0；inflight=2 ≤ inflight=1；计数按次清零；
- **补丁惰性**：120 个调度场景 × 4 步 = 480 行，打补丁与未打补丁树的 `gen_s`／`clock_sleeps`／`evicted`／`surplus` **逐字段相同**（`inert=true`）。

读数：[sim-polls.json](raw/sim-polls.json)。用法：

```bash
# 服务器窗口：先把补丁打到受测树，再跑 4 卡 inflight=1 臂，读每步 training/sampler/blocking_polls
patch -p1 --fuzz=0 < poll-count.patch
# 本机：换树自检
/tmp/m5-trf-venv/bin/python3 sim-loop.py --tree <树> --compare <未打补丁树> --selftest
```

## 七、对 TM-008 三条读法的影响

1. **收益不是"每步固定 2 s"**，而是"每步在网格上的向上取整"。落在格子中部的配置（4 卡固定批，D≈1.6）几乎不付量子，收益 −2.0%；压在边界上的配置（2 卡固定批，D≈2.0）一半的步多付一整格，收益 −3.2% 且二态消失（sd 1.05→0.23）。DAPO 臂因为多轮派发，斜率落在两者之间。
2. **"0.5 不是通用解"有了机制解释**：能否消掉量子取决于 D 与 0.5 网格的关系，而不只看 P 的大小。
3. **对外写作的边界更清楚**：可以写"这是释放时刻的量化，收益等于被消掉的取整量"，不能写"每步省 2 s 的等待"。同时保留原来的边界——`separate_async` 的 rollout-ahead 区间里训练步不阻塞在 `sample()`，收益为 0（§13.54）。

## 八、边界与未做

- **零 GPU 读数。** 全部为归档日志重算 + CPU 上执行真实源码；"生效值"是虚拟时钟下的控制流，不是服务器实测。
- **逐步配对假设同 workload**：2 卡臂 3 个边界步已证明该假设在 D 接近边界时会失效；4 卡臂的 D 方差小所以 12/12，但这不等于模型对任意配置都同样准。
- **c 的归属未拆**：约 0.16 s 落在 `timing_s/gen` 内、最后一个 sleep 之后；本轮只测到它是常数，没做插桩区分（元数据回读／选择／materialise／计时边界）。
- **计数器尚未在服务器上跑过**：4 卡 `inflight=1` 臂仍等 ≥4 卡空闲窗口；开窗前先跑 [preflight-g4.py](../verl-v1-poll-quantum-dapo-g4/preflight-g4.py)。届时预期：`blocking_polls ≥ 2`（每次补发轮次各需一次轮询；若实测恒为 1，则归档斜率差异不能用轮数解释，需另找来源）。
- 未触上游；补丁只在本目录，未 push 到任何 verl 分支。
