# verl `use_prefix_grouper` 的训练侧副作用值多少：组完整性让 DP 均衡差 0.0–6.6%

2026-11-02，M1。配合 [open-source/verl/evidence/prefix-grouper-inert](../../open-source/verl/evidence/prefix-grouper-inert/readme.md)。

**不是 GPU 实测，不是端到端**。直接抽取上游 `verl/utils/seqlen_balancing.py` 的函数源码运行（AST 取源码 + 最小 torch 替身），**跑的是上游算法本身**。

## 一句话结论

上一轮确认：`use_prefix_grouper=True` 在 FSDP 引擎上**不启用前缀共享前向**，但 trainer 侧的两件事照常生效。本轮量化这两件事相对"正常路径"的净差异：

- **跳过批内重排**：按 §13.39，在 `max` 代价模型下它不是损失，反而是**改善**（跳过不亏）。所以这半边**不算代价**。
- **组级均衡**：这是真正的代价，但**很小**——DP8、批 1024 时最重 rank 只比逐条均衡重 **1.27%**；代价随批增大迅速消失（批 16384 时 0.02%），小批时明显放大（批 256 时 **6.61%**）。

## 为什么做

上游接受度低（维护者已转向 MAGI attention，见 [#7202](https://github.com/verl-project/verl/pull/7202) 关闭未合并），所以"提 issue 请修"意义有限。但作为掘金 B 类，需要回答一个更实际的问题：**用户误开这个开关，到底损失了什么？** 如果损失接近零，那这个发现的价值就只是"文档不清"；如果损失可观，才值得推动上游。

## 方法

`_balance_batch` 在开关为真时做两件事：

1. `get_group_balanced_partitions(...)` —— 组级 Karmarkar-Karp，**同 uid 必须在同一 rank**；
2. **跳过** `// Place smaller micro-batches at both ends` 那段 rank 内重排。

本实验只量第 1 件（第 2 件已由 §13.39 定量：跳过反而是负 optim，不构成损失）。

**负载模型用上游自己的** `calculate_workload(L) = 24576·L + L²`，而不是裸长度——它在实用长度区间接近线性（L=400→800 只涨 2.03×），要到 L≈24576 二次项才占优。

**长度生成**：对数正态，中位 400，`group_rho` 控制同 prompt 各条回答的长度相关性（真实模型里同 prompt 的 n 条共享难度）。

## 结果

### Q1：组完整性的代价随规模变化

`imbalance = 最重分区负载 ÷ 平均分区负载`（1.0 = 完美均衡）。批固定 1024、n=5、DP8：

| 批大小 | 逐条均衡 | 组级均衡 | 代价 |
|---|---|---|---|
| **256** | 1.0263 | 1.0942 | **+6.61%** |
| **1024** | 1.0094 | 1.0222 | **+1.27%** |
| 4096 | 1.0032 | 1.0051 | +0.18% |
| 16384 | 1.0010 | 1.0012 | +0.02% |

**单调递减**，且在小批区显著。上游示例用的是 `train_batch_size=1024`，正好落在 +1.27% 这一档。

### Q2：DP 规模和 n 的影响（批固定 2048）

| 配置 | 逐条 | 组级 | 代价 |
|---|---|---|---|
| DP4, n=4 | 1.0016 | 1.0084 | +0.67% |
| DP4, n=5 | 1.0013 | 1.0107 | +0.94% |
| DP8, n=4 | 1.0062 | 1.0187 | +1.25% |
| DP8, n=5 | 1.0060 | 1.0215 | +1.54% |

DP 越大、n 越大，代价越大——因为每组是不可分的整体，组越大粒度越粗。

### Q3：组内长度相关性（rho）的影响

| rho | 逐条 | 组级 | 代价 |
|---|---|---|---|
| 0.00 | 1.0049 | 1.0198 | +1.48% |
| 0.50 | 1.0060 | 1.0215 | +1.54% |
| 0.75 | 1.0053 | 1.0283 | +2.28% |
| **1.00** | 1.0010 | 1.0341 | **+3.31%** |

**反直觉但可解释**：rho 越高（同组各条长度越接近），组越是"齐整的大块"，逐条均衡可以打散、组级均衡不能，因此代价**上升**而不是下降。rho=1 是最坏情形。

### Q4：正确性对照（证明跑的是上游代码）

不变量测试全部通过：两种分区**都覆盖全部下标、不重不漏、各分区等长**；组级分区**确实把同 uid 放在同一分区**；而逐条分区**确实会拆开同 uid**（负向对照——若一条都没被拆开，组完整性就没有代价可言）。

## 与上游发现的关系

| | 结论 |
|---|---|
| 引擎侧（上一轮） | 前缀共享前向**不生效** — 功能缺失 |
| trainer 侧（本批） | 组级均衡的代价 **0.0–6.6%**，批 1024 时 1.27% |
| 跳过重排 | 按 §13.39 **不是损失** |

所以"误开开关"的净影响是：**功能没拿到，代价只有 0~6.6% 的 DP 不均衡**（且不进整步墙钟，因为 `train_batch_size` 决定了每 rank 的实际样本量——这里量的是**负载**不均衡，不是样本数不均衡）。

## 边界

- **无 GPU、未运行 verl**；上游函数以 AST 提取后注入替身运行，替身只实现 `+ * ** .item()` 与 `zip(strict=)` 垫片。
- 只量 **DP 负载不均衡**，不是墙钟。真实影响还取决于 backend 是否按 token 计费、是否有 padding 填充；本实验不做换算。
- 长度分布是**构造参数**（中位 400、对数正态），不来自任何训练日志。
- `group_rho` 的真实取值**未实测**——这是本仓库 §13.38 已登记的同一条开放项。
- 10 个单测、`--verify` 连跑两次通过，sha256 见 [run-info.json](run-info.json)。
