第一部分：宏观认知 —— 这是什么？为什么？

1.1 一句话定义

DeepSeek Harness（简称 dsh）是一个 AI 智能体运行框架——它为 AI Agent 提供运行所需的一切基础设施（模型调用、工具执行、沙箱隔离、会话管理、Web UI），而且所有这些基础设施都是可插拔的插件。

1.2 什么是 Harness？

在 Agent Infra 领域，Harness（脚手架/测试框架）指的是一套为 AI 智能体提供运行时环境的系统。类比：

  • 如果 AI 模型是「大脑」，那么 Harness 就是「身体 + 感官 + 四肢」——它让大脑能看文件、敲命令、上网搜索、调用工具
  • 如果 AI Agent 是一个员工，那么 Harness 就是他的办公环境——电脑、终端、文件系统、网络、审批流程
  • 类比其他项目：OpenAI Codex CLI、Claude Code、Cursor 都是某种形式的 Harness

1.3 为什么需要「一切皆插件」？

传统 Agent 框架把功能硬编码在核心里——换模型要改代码，换沙箱要改代码，换 UI 还是要改代码。dsh 的哲学是：

核心原则：没有特权核心。模型适配器、工具注册表、会话日志、甚至 Agent Loop 本身——全都是插件。换一个插件 = 换一个能力，无需动框架。

这意味着：

  • 你想用 OpenAI 而不是 DeepSeek？换一个 LLM 适配器插件
  • 你想在 Docker 沙箱里执行？换一个 Sandbox 插件
  • 你想用终端 UI 而不是 Web UI？换一个 Surface 插件
  • 你想给 Agent 加一个新能力？写一个新插件

第二部分：核心概念 —— 五个关键思想

理解 dsh 不需要读懂全部 56 万行代码，只需要掌握五个关键思想，它们都来自底层框架 Cordis：

2.1 思想一：插件即服务

一个插件就是一个实现 Service 的对象。它可以是一个函数（最简单形式），也可以是一个类（更结构化）。插件通过 apply(ctx, config) 接收上下文和配置。

// 函数式插件 —— 最简单
export function apply(ctx: Context, config: Config) {
    ctx.tools.register('my-tool', ...)
}

// 类式插件 —— 更结构化
export class MyService extends Service {
    static inject = ['tools', 'llm']
    constructor(ctx: Context, config: Config) {
        super(ctx, 'myService')
    }
}

2.2 思想二：上下文即服务仓库

ctx 是所有服务的容器。插件通过稳定的 ctx.<key> 来发现和消费服务，而不是直接 import 具体实现：

// 不要这样写（紧耦合）：
import { deepseek } from '@deepseek-ai/dsh-llm-deepseek'

// 应该这样写（松耦合）：
const models = ctx.llm  // 谁实现的不重要，接口一样就行

2.3 思想三：声明式依赖

插件通过 inject 声明自己需要哪些服务，框架会等这些服务都就位后才启动插件。不需要手动管理加载顺序：

export const inject = ['tools', 'shell', 'systemPrompt']
// 等到 ctx.tools、ctx.shell、ctx.systemPrompt 都有了，才执行 apply()

2.4 思想四：类型化事件

插件之间通过类型化事件通信，有五种派发模式：

模式方法语义场景
emitctx.emit()广播通知，不等结果状态变更通知
waterfallctx.waterfall()瀑布链，每个监听器包裹 next()请求拦截/修改
parallelctx.parallel()所有监听器并行执行独立副作用
serialctx.serial()按序执行，可短路有序决策
bailctx.bail()同步，首个非空返回即停快速查找

2.5 思想五：注册即可逆效应

每一个注册（工具、提示词、事件监听器）都通过 ctx.effect() 或 ctx.on() 完成，卸载插件时所有注册自动撤销：

ctx.effect(() => {
    const dispose = ctx.tools.register('my-tool', ...)
    return dispose  // 卸载时自动调用
})

这就是为什么热重载在 dsh 里是安全的——插件卸载 = 一切归零，插件重装 = 一切重建。

4.1 Cordis —— 底层插件框架

dsh 的插件系统并非自研，而是基于 Cordis 框架（源自 Koishi 聊天机器人框架），以 vendor 方式内嵌在 vendor/ 目录。Cordis 提供：

Vendor 包角色
cordis核心框架：Context、Service、Fiber、事件总线
loader配置驱动的插件加载器
includeYAML 组合与补丁
group插件分组管理

timer定时任务
logger-console控制台日志
cosmokit工具库
schemasterySchema/验证框架

4.2 Fiber 生命周期

每个插件实例是一个 Fiber，有以下状态：

状态含义
PENDING等待依赖服务就绪
LOADING插件回调正在执行
ACTIVE加载完成，提供服务
FAILED回调或配置验证抛出异常
UNLOADING正在卸载（执行清理函数）
DISPOSED已永久移除

关键特性：依赖服务丢失时 Fiber 自动卸载并撤销所有效应；依赖恢复时自动重新激活。

4.3 能力缝隙（Capability Seam）模式

这是 dsh 最核心的架构模式。每个能力由三个角色组成：

┌─────────────────────────────────────────────────────────────┐
│                    Capability Seam（能力缝隙）                 │
│                                                               │
│  ┌──────────────────┐    ┌──────────────────┐    ┌─────────┐ │
│  │  Service          │    │  Service          │    │ Consumer │ │
│  │  Definition       │    │  Provider         │    │ (工具)   │ │
│  │  (接口声明)        │    │  (具体实现)        │    │ (消费者) │ │
│  │                   │    │                   │    │         │ │
│  │  dsh-shell        │    │  dsh-bash-local   │    │tool-bash│ │
│  │  ctx.shell        │    │  dsh-bash-sandbox │    │         │ │
│  │                   │    │                   │    │         │ │
│  └──────────────────┘    └──────────────────┘    └─────────┘ │
│                                                               │
│  换一个 Provider → 整个产品行为改变，无需动 Consumer 或 Loop     │
└─────────────────────────────────────────────────────────────┘

例如，把文件系统和子进程的 Provider 指向远程沙箱，Bash、PTY、LSP 工具就自动在远程执行——无需改动任何工具代码。

第五部分：Agent Loop —— 智能体的心跳

5.1 什么是 Agent Loop？

Agent Loop 是让 AI 智能体「活」起来的循环——它接收输入、调用模型、执行工具、把工具结果喂回模型，直到任务完成。在 dsh 中，Agent Loop 本身也是一个插件 dsh-agent-loop。

5.2 Turn / Step 模型

Turn（对话轮次）
├── Step 1（一次模型调用 + 工具执行）
│   ├── 组装 Prompt + 工具 Schema
│   ├── agent/pre-step (waterfall: 拒绝或放行)
│   ├── 调用 LLM (llm/stream waterfall)
│   ├── 接收 assistant/chunk* → assistant/message
│   ├── 解析 tool/call*
│   ├── tools/pre-execute → tools/execute → tools/post-execute
│   └── tool/result*
│
├── Step 2（如果工具结果需要再次调用模型）
│   └── ...同上...
│
└── Turn 结束（agent/turn-stopping serial 决定是否停止）

关键概念：

  • Step = 一次模型请求 + 它触发的工具调用
  • Turn = 零或多个 Step，从用户输入开始到无需继续为止
  • 模型可见 = 必须记录：任何到达模型请求的内容，必须能从会话日志重建
  • 输入通过一个收件箱到达驱动器；注入的上下文在收件箱中排队等待

5.3 事件拦截点

整个循环暴露了多个事件拦截点，让你可以在不修改 Loop 的情况下改变行为：

事件模式作用
agent/pre-stepwaterfall拒绝或修改即将发送给模型的请求
agent/requestwaterfall修改 LLM 调用配置
llm/streamwaterfall拦截/修改模型流式输出
tools/pre-executewaterfall工具执行前拦截（审批、修改参数）
tools/executewaterfall替换工具执行逻辑
tools/post-executewaterfall工具执行后处理（日志、遥测）
agent/turn-stoppingserial决定 Turn 是否结束

5.4 Scope —— 每个 Agent 的独立世界

当多个 Agent 同时运行时（如子智能体），每个 Agent 有自己的 Scope。Scope 提供：

  • 注册隔离：Agent A 注册的工具不影响 Agent B
  • 事件路由：Agent A 的事件只会被 A 的监听器接收（父 Scope 可以收子 Scope 事件）
  • Preset 绑定：每个 Agent 绑定到一个 Preset 的「常驻挂载」，继承其工具和提示词

第六部分：会话系统 —— 事件溯源与持久化

6.1 事件溯源（Event Sourcing）

会话日志是整个系统的唯一真相来源。所有模型可见状态都从日志推导。关键不变量：

核心不变量：模型可见 = 必须记录。任何到达模型请求的内容，必须能从会话日志重建。如果你想让 Agent 「看到」新东西，必须定义新的 SessionEvent。

核心会话事件类型：

事件含义
turn/start, turn/end对话轮次边界
step/start, step/end模型调用步骤边界
user/message用户输入
assistant/chunk流式输出片段
assistant/message完整的助手消息
tool/call, tool/result工具调用与结果
todo/write待办事项更新
request/header, request/context请求上下文

6.2 持久化后端

两个可互换的持久化后端：

后端格式特点
JSONL（默认）每会话一个 .jsonl[.zstd] 文件人类可读，支持 zstd 压缩，崩溃修复（撕裂帧恢复），原子写入
SQLite单数据库文件支持 seek-capable 后缀读取（不读全量），事务原子性，单调递增修订版本

6.3 写后 batching

实时事件不会立即写入磁盘，而是通过 Write-Behind Batching 缓冲：

  • 固定截止时间（默认 200ms）批量写入
  • session/flush 或会话销毁时强制刷新
  • 写入失败时保留缓冲，暂停定时器直到下次显式 flush
  • 每个会话有独立的 promise chain，写入不会交错

6.4 崩溃修复

加载时，持久化协调器会：

  1. 读取存储前缀
  2. 检测撕裂尾部（JSONL 通过 zstd 帧扫描，SQLite 通过行间隙）
  3. 追加合成的 interruptedTurnClosers 来平衡日志

6.5 投影（Projection）

投影是从会话日志折叠出的派生视图，用于避免每次都重放全量日志：

  • tokenUsage：累计 Token 使用量
  • contextPressure：上下文窗口占用比
  • sessionStats：Turn/Step 计数、耗时统计
  • title：会话标题

投影支持快照缓存——持久化检查点，冷启动时从缓存 + 后缀重放恢复。

第七部分：LLM 层 —— 模型适配与流式推理

7.1 适配器注册表

ctx.llm（LlmRuntime）是 LLM 能力的中心：

  • 多个适配器注册到不同的 Provider 路由（如 deepseek-official、openai）
  • registerAdapter(providers, adapter) 返回句柄，支持原子替换
  • llm/stream waterfall 拦截每次模型调用

7.2 DeepSeek 适配器

直接使用 fetch() + SSE 调用 DeepSeek OpenAI 兼容接口：

  • 支持 thinking 模式（reasoning_effort: high/max）
  • 流式输出：text-delta、reasoning-delta、tool-call-delta
  • 空闲看门狗（默认 300s 超时）
  • 归属头：每个请求包含 x-deepseek-harness-user-id
  • 错误映射：401/403→AUTH, 429→RATE_LIMIT, 400 context→CONTEXT_WINDOW_EXCEEDED, 5xx→SERVER

7.3 pi-ai 多提供商适配器

通过 @earendil-works/pi-ai 库支持 OpenAI、Anthropic、Azure、Bedrock、Vertex 等：

  • 每个路由有独立的 apiKeyEnv、baseURL、协议、模型列表
  • 支持 OpenAI-compatible 和 Responses 两种协议
  • 通过 GET /models 自动发现模型

7.4 流式协议（StreamChunk）

Chunk 类型含义

7.5 重试策略

在 agent/request-error waterfall 上执行：

  • 指数退避 + 抖动：initialDelayMs * 2^(retry-1) * jitter
  • 尊重 Retry-After 头
  • 重试事件持久化到会话日志
  • 插件销毁时通过 AbortController 取消等待

第八部分：通信架构 —— Host-Client-SDK 三角

8.1 Web 模式（Host ↔ Browser）

Browser (React App)                    Host Process (Node.js)
═══════════════════                    ══════════════════════

POST /api/<method>  ───── JSON ──────→  node:http WebServer
                     ←──── JSON ──────  Typert Gateway / API Proxy

WebSocket /api/events.mux  ←══════════  Mux 事件流
WebSocket /api/events.host ←══════════  Host 事件流

信任边界：Host header 必须是 loopback 或匹配 trustedHosts
特权方法（设置、凭证、桌面操作）仅限 loopback 访问

8.2 SDK 模式（Client ↔ Runtime via stdio）

Client Process                     Runtime Process
══════════════                     ══════════════

stdin ──── newline-delimited ────→  JSON-RPC Server
stdout ←── JSON-RPC 2.0 ──────────  (stdio only, no logging)

initialize { cwd, provider, model }
session/prompt { sessionId, content }
← session.event { sessionId, event }  (流式推送)
← session.status { status }
shutdown

关闭阶梯：stdin EOF → SIGTERM → SIGKILL

8.3 ACP 模式（Agent Client Protocol）

自动化专用 JSON-RPC 服务器，遵循 ACP 规范。支持 initialize、session/new、session/prompt、session/cancel。只输出已提交消息（无原始 chunk/reasoning）。

8.4 Typert —— 类型反射与 RPC 系统

dsh 自研的类型反射和 RPC 框架，贯穿构建时 TypeScript 分析到运行时验证分发：

  • 构建时：TypeScript 分析器生成 FaceModel / TypeGraph、Zod schema
  • 运行时：@Remote 装饰器声明 RPC 方法，Typert 自动发现和注册
  • 双面构建：Host 构建产出 Host 反射 + Client Remote 投影；Client 构建消费这些投影
