DeepSeek-V4 的 KV Cache 管理

project: infer_vLLM · 内容转写自 Mengqing Cao 博客（2026-06-09）

一、模型侧的创新

mHC 残差连接

在 attention + MoE 的架构上对残差连接做了一处创新：计算前先用 hc_pre 将 hidden states 降维，降维后的状态参与 attention / MoE 计算，计算后经 hc_post 升维，再与残差线上的 hidden states concat 作为下一层输入。mHC 在尽量保留更多前层信息的同时，不增加主体 attention / MoE 的计算量。

KV 压缩（核心创新）

  • 通过可训练的 compressor 模块对 KV Cache 进行压缩，设计了两种压缩比 4 和 128，两种压缩比的 attention 层交替出现
  • MTP 层不压缩；Flash 模型的第 0/1 层不压缩

三种 attention 层的 KV 形态

层类型名称KV 构成
c4（压缩比 4）CSA · Compressed Sparse Attentionsliding window + compressed kv + indexer 稀疏选择（同 V3.2 DSA 机制，indices 指向压缩后的 kv）
c128（压缩比 128）HCA · Heavily Compressed Attentionsliding window + 主 compressor，无 indexer 稀疏化（≈ c4 去掉 topk select）
不压缩层Sliding Window MLA仅 sliding window kv

需要框架侧管理的 cache 由此扩展到多种：swa cache、compressed kv cache、compressed indexer kv cache；此外 compressor 在不满压缩比时需暂存 kv state 与加权和 softmax 的 score state，因此每个 compressor 还对应两个中间暂存 cache：

层cache 清单
c1swa cache
c4swa cache、compressed kv cache、compressed indexer kv cache、c4a kv/score state、c4i kv/score state
c128swa cache、compressed kv cache、c128a kv/score state

c4a = c4 层的 attention，c4i = c4 层的 indexer；压缩 kv 满压缩比后才写入 compressed kv cache。

二、vLLM（GPU）侧的实现

KVCache planning 基于 UniformTypeKVCacheSpecs + Hybrid Memory Allocator（详见另一篇转写），总体思路：

  • 先用 UniformTypeKVCacheSpecs 对 page_size 差异大的 specs 做一层 warp，再在多个 UniformType 组之间做 hybrid kv 共享
  • UniformType 组内部划分为 3 个大小不一的 tensor：既实现组间共享同一 block pool，又避免 HMA 的 page_size 对齐引入过多 wasted pad
  • 管理面看到的 block_size 是 256，但每个 spec 的实际 block_size 并不相等——压缩发生在 block_size 这一维：kernel 侧实际 block 只有 block_size // compress_ratio 个 slots

运行时实例（DeepSeek V4 Flash，43 层）

  • 层结构：0/1 swa；2～42 偶数层 c4、奇数层 c128；分组组大小 22 → 22 × 3 个 KVCacheTensor，每个 tensor 被全部 5 个组共享
  • 长度 258 的请求按组分配：group1/2/3 → cdiv(258,256)=2，group4 → cdiv(258,8)=33，group5 → cdiv(258,4)=65
  • group4/5 是 SlidingWindowManager：前 32/64 个 block 立即 free_blocks 释放，实际占用仅 1 个 block
  • slot_mapping 压缩：vllm/v1/attention/backends/mla/compressor_utils.py 的 get_compressed_slot_mapping——按压缩后的 block_size 计算 slot_mapping，不满压缩比的位置置 -1，reshape_and_cache 对 -1 位置跳过写入，从而在 attention 后端实现压缩存储

三、vLLM Ascend 侧的定制

Ascend 算子限制：attention 算子支持的最小 block_size 为 16，性能推荐 128——这是与 GPU 方案分道扬镳的根本原因。

  • 定制点 1：c128a 的物理大小比 GPU 大数倍，单独一个 KVCacheTensor 会引入巨大 pad；做法是让 c128a 也成为与其他组共享 tensor 的一个组，仅引入一个组即消除大量临时 pad blocks（代价：实现与 vLLM 略有不同的 KVCache Planning）
  • 定制点 2：压缩维度改为 num_blocks 维而非 block_size 维——scheduler 为 num_tokens 申请 blocks 时提前压缩为 num_tokens // compress_ratio，分配时即为 compressed kv 只分配 1/compress_ratio 倍 blocks；代价是 block_id 已被压缩，ModelRunner 需适配压缩 position id 与 slot_mapping（参考 vllm_ascend.utils.get_compressed_pos_and_indices 与 vllm_ascend.worker.block_table.MultiGroupBlockTable.compute_slot_mapping）
