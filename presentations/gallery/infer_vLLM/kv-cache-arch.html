vLLM 中的几种 KVCache 分组机制

project: infer_vLLM · 内容转写自 Mengqing Cao 博客（2026-06-09）

一、统一术语

  • KVCache 类型：不同的 KVCacheSpec
  • 大小：一个 block 占的物理内存字节数，通常为 block_size × num_head × head_dim × sizeof(cache_dtype)

二、三种分组方式

1. 统一的 KVCacheSpec 组

每个 Attention 层的 KVCache 完全一致（类型、大小都一致）。最广泛最基础，几乎所有非混合 Attention 模型都属于这一种——典型如 Qwen2.5、DeepSeek V3.1。每层一块 buffer，每块 buffer 上 num_gpu_blocks 个 blocks，由 KVCacheManager 统一从 BlockPool 调度。

2. 类型统一的 KVCacheSpec 组

不同层 KVCache 类型相同但大小不同。典型：DeepSeek V3.2（indexer cache 层与 MLA 层量化策略不一致）、MiniCPM 4.1、spec decode / MTP 层中 kv head 数与主模型不一致（vLLM PR #25101）。每层仍各有一块 buffer，但大小不一；同一 token 在不同层分配的 block id 相同。

3. 混合 KVCacheSpec 组（HMA 的核心）

不同层 KVCache 类型不同、大小不一定一样。典型：Gemma3、Qwen3-Next、Qwen3.5。

问题的起点：没有 HMA 时 vLLM 给每层分配同样大小的 buffer。而 linear attention 层每个请求所需 KVCache 总量是固定的（只需 N=1 个 block），却被强行为其分配 NUM_BLOCKS 个 block——且 Qwen3-Next 中 linear attention 层数是 full attention 层的 2 倍以上，浪费被放大。

三、为什么 UniformTypeKVCacheSpecs 解决不了

  • UniformType 机制仍要求每层 block 数量相等：KVCacheCoordinator 只有一个 block pool、只有一个 SingleTypeKVCacheManager，同一请求各层分配的 block id 相同
  • 若拆多个 block pool 给 linear / full 分别预留，则必须预估 linear 层运行时的 block 峰值——考虑 prefix cache 时无法预知命中数；按最保守方式预留会退化为每层同样数量的 block

四、HMA 的核心设计

不同层共享同一块 buffer：一个 block pool、一份 blocktable，从而减少 KVCache 浪费与碎片化。

以 Qwen3-Next 为例：full attention 与 linear attention 层数比 1:3，shared_by 中 1 层 full + 3 层 linear 共享同一 buffer；对一个 token，每个 KVCacheTensor 上分配 4 个 block id（共享组内每层一个）。

HMA 两个关键点

  1. page size 对齐：不同类型 KVCacheSpec 的 page size（一个 block 的物理内存大小）必须对齐。vLLM 当前两种对齐方法：放大 block size 为原来 x 倍，或添加 pad。共享同一 buffer 的各类型仍各自有一份内存视图——物理内存同一片，解读不同。
  2. 解耦 kernel block size 与 KV page size：attention 算子接收的 block size / block table / slot mapping 都基于算子支持的 block size 计算；调度侧仍用大 block size 做分配（一次分配 x 个 kernel 侧 blocks）。该特性让更多 attention backend 能接入 HMA（vLLM PR #24486: Decouple Kernel Block Size from KV Page Size）。
