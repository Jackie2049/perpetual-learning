1.2 生态定位

Lego-RL 不做训练引擎本身，而是把「真实的 coding-agent harness 环境」接到 verl 上：verl 负责 PPO/GRPO/GSPO 优化与分布式，Harbor 负责沙箱与可执行验证，Lego-RL 解决两者之间的三件事——rollout 的保真捕获（in-process proxy）、失败/reward 污染的处理（轨迹过滤 + reward 完整性防御）、以及运行期可观测（agent plugin + Live UI）。支持一个新 harness 只需写一个薄适配器，训练管线完全共享。它与我们此前研究的 verl、rLLM 属于同一生态位竞争，但选择了「模型 API 边界观察」路线（见第 6 章对比）。

2. 研究动机：为什么需要 Harness-Native RL

2.1 背景：coding agent 的 RL 与普通 LLM-RL 不同

训练 coding agent 需要优化的是长程行为：一条 rollout 可能包含数十次模型调用、仓库检查、工具调用、代码修改、依赖安装、测试执行，最后才得到一个稀疏的可执行 reward。这些轨迹由原生 agent harness 生成——harness 负责 prompt 构造、工具管理、上下文管理、执行状态。因此优化目标应当是「该 harness 控制流所诱导的策略行为」，而不是某个框架自定义的 rollout 接口下的行为。这是「harness-native」立场的根源：你在什么 harness 里训，就在什么 harness 里跑（论文用 KAT-Coder 的例子证明了这一点：它在自己报告的 Claude Code 下 +3.4，在 OpenHands SDK 下 −0.4——换 harness 收益不迁移）。

2.2 三大痛点

痛点具体问题后果
① harness 不可侵入一般 RL 框架要求 agent 适配框架定义的 rollout 接口（OpenHands 系要改初始化、换工具集、写自定义终止逻辑）训练的是「改过的 agent」，行为分布偏移；每个新 agent 都要重写一套集成
② rollout 保真度断裂harness 会压缩/重序列化/重写对话历史；事后从最终轨迹反推 token 序列 ≠ 采样时刻的真实序列；训练端重算 log-prob 与 rollout 不一致。稀疏 MoE 还会引入路由不一致（训练时选的专家 ≠ rollout 时选的专家）PPO/GRPO 类算法对 log-prob 极其敏感——log-prob 就是 importance ratio 的输入，错一丁点梯度就偏
③ 沙箱与 reward 不可信沙箱崩溃、依赖错误、verifier 配置错误、超时、reward hacking 都会污染二值 reward；异步管线中失败跨 stage 传播，难以定位成本极高的轨迹被丢弃，或把「环境噪声」当「策略学习信号」

2.3 形式化目标与「保真」的定义

论文把任务写成 x = (q_x, R_x, V_x)（问题陈述、仓库环境、可执行 verifier），rollout 是模型 API 处真实交换的 prompt–response 序列 τ = ((c₁,a₁),…,(c_T,a_T))，verifier 给终态二值 reward。训练目标用 group-relative advantage（即 GRPO 式）与 GSPO 序列级损失：

3. 主要方法：四大支柱

3.1 支柱一：薄适配层 —— 不改 agent 一行代码

支持一个 harness = 一个 adapter：负责在沙箱里启动 agent、把它的模型调用指向 in-process proxy、执行完返回交互数据。论文支持的三种原生 harness：

  • OpenHands SDK：容器内跑轻量 SDK（openhands-sdk==1.33.0），Jinja2 模板渲染 user 指令，env 注入 LLM_BASE_URL/LLM_MODEL/SKILL_PATHS；
  • Claude Code：走 Anthropic Messages API，env 注入 ANTHROPIC_BASE_URL 指向 proxy 的 /sess/{id}/v1（按 trial 覆盖，不走独立 LiteLLM）；CLAUDE_CODE_ATTRIBUTION_HEADER=0 关掉 billing hash 头以保 prefix cache；
  • OpenCode：OpenAI 兼容 hosted_vllm provider，env 注入 HOSTED_VLLM_BASE_URL + OPENCODE_TEMPERATURE。

任何会讲 OpenAI/Anthropic API 的自定义 scaffold 都可以直接复用同一套 agent-loop 接口（verl 的 AgentLoopBase 注册表）。

3.2 支柱二：保真 rollout —— in-process proxy 在生成时刻捕获一切

核心模块 src/verl_patch/agent_loop/vllm_chat_completion_proxy.py（约 2400 行）：一个与 verl rollout 引擎同进程的 aiohttp 服务器，同时讲 OpenAI Chat Completions 和 Anthropic Messages 两种协议，但内部是 token-in/token-out：用 verl 的 tokenizer apply_chat_template 把消息 tokenize 后直接调 server_manager.generate(prompt_ids)，在响应瞬间把 token ids、逐 token log-prob、response mask、MoE 路由决策（R3）全部归档进 session 轨迹。要解决的工程难题都在「history rewrite」上：

  • 消息级前缀对齐：逐轮对增量消息做 apply_chat_template（去重 generation-prompt、回填 EOS 尾 token），新请求必须是已归档快照的前缀扩展，否则进入 rebuild 路径；
  • tool-call 身份锚定：Claude Code 会以任意方式重序列化 tool_call 的 arguments（JSON↔list、key 重排、schema 默认填充），但 id 恒不变——按 id 匹配即可吸收 207/222（93%）的重序列化差异，只有真正的历史改写（如动态插入 system-reminder）才触发重建；
  • 重建时救回 log-prob：重建路径只把「共同前缀」的旧 log-prob 拷贝回来（token 的 log-prob 取决于完整左上下文，共同后缀不可复用），并可用 vLLM prompt_logprobs 重算分歧尾部（默认开、OOM 可 kill-switch）；
  • 子 agent 隔离：Claude Code 的 Task 子 agent（Explore 等）与主会话共享 session_id 但 system prompt 不同——按 system prompt 指纹路由到隔离的、不入训练的非归档状态（论文实测把混入率从 6.3% 降到 0%）；OpenCode 的标题生成内部请求同理；
  • 会话级准入调度：高 KV 压力时按「会话所有权 + prefix-cache 命中率」准入（vLLM patch 新增 kv_cache_usage_probe/prefix_cache_probe 无副作用探针），保 prefix 驻留。

归档结果通过 AgentLoopOutput 交给 verl：prompt_ids、response_ids（截到 response_length）、response_mask（1=模型 token，0=工具/用户 token）、response_logprobs、routed_experts（R3）、以及 termination_reason 等 extra_fields。MoE 训练端用 R3（rollout routing replay）：vLLM 侧 capturer 在推理时把每层 top-k 专家选择写入共享内存（routed_experts_capturer.py，uint8 缓冲 + R3_BUFFER_FACTOR=5 修复混合注意力模型低估 ~4 倍的问题），训练时 qwen3_5_router_replay.py 包裹 router 的 forward：RECORD 记录索引，REPLAY_FORWARD 用捕获索引覆盖 top-k 选择并重归一化——保证训练前向与 rollout 走同一批专家。

3.3 支柱三：训练与扩展 —— 异步、staleness、轨迹过滤

  • 全异步 rollout：FullyAsyncRollouter（verl experimental）解耦轨迹生成与优化，agentic rollout 长尾重——同步批次会被最慢的 10% 轨迹拖住（离线实测：最慢 10% 占 24.5% 总工作量，31 次 batch 边界 stall 中位数 38.7 分钟）。异步下每次权重同步时被中断的部分 rollout 由 AsyncLLMServerManager 自动续生（partial_rollout: True），staleness 有界（模板默认 STALENESS=1.0，配置 staleness_threshold: 0.1、每 4 步同步一次参数）；
  • 终止感知的轨迹准入：统一的终止分类法（agent_completed / overlong / max_turns_reached / timeout / env_setup_failed）。trajectory_filter.py（verl 新增模块）把环境失败/超时/上下文溢出/超长轨迹从训练中剔除：零化其 reward、改写 uid 为单例组（从 GRPO 组统计中摘除）、事后零化 advantage——batch 形状不变，三重保险。论文实测丢弃率：Claude Code 7.1%、OpenHands SDK 2.4%、OpenCode 6.4%；
  • 算法/后端：PPO / GRPO / GSPO × FSDP / VeOmni / Megatron；生产用 use_rollout_log_probs=True（训练直接吃 rollout 捕获的 log-prob）+ rollout_correction.bypass_mode（log-prob 一致性足够高时跳过 IS 校正，降低方差）。

3.4 支柱四：沙箱化 reward —— 隔离、懒拉取、反作弊

  • K8s/Docker 双后端：每个 trial 一个全新 pod/容器；harbor_patch/environments/kubernetes.py 是通用 K8s 实现（非 GKE 专用），Docker 端支持远程 daemon；
  • 启动优化：Nydus 懒拉取（按需流式取镜像块，冷启动中位 1.7×、最大 23× 提速；网络流量 21.6GB→1.59GB、磁盘写 65.6GB→5.29GB）、预构建任务镜像（33.2×）、agent 运行时只读挂载而非安装（15.4×）；
  • reward 完整性防御（论文附录 A 实测的六类失败模式 + 对策）：
    失败模式实测发生率防御
    读 git 历史找答案4.6–20.5%agent 阶段把历史 rebase 成单 commit，判分前恢复

同一 harness 版本与评测协议（温度 0.7、200 turns、200k 上下文）下由作者实测。Lego-RL 训练后模型在三个 harness 下均超过下一代 base（+3.0/+4.8/+6.0 pp）和 KAT-Coder-V2.5-Dev（+3.4/+1.4/+1.8 pp）——即「在 3.5 上做 RL 胜过升级 base 模型」。收益是 harness 特异的：KAT-Coder 在它报告的 Claude Code 下 +3.4，在 OpenHands SDK 下 −0.4。README 对 OpenCode 列的 KAT 分数为 61.2，与论文表（64.8）不一致，以论文为准。

5.3 数据管线与 reward 完整性（§4.3）

  • 任务筛选漏斗：36,884 个 OpenSWE 候选 → 规则筛选（有效性/仓库多样性/复杂度）22,806 → 构建 + verifier 验证 21,681（其中约 2.5% 的 verifier 逻辑会错误应用参考 patch）→ Qwen3.6-27B + OpenHands SDK 四次 rollout 中解出 1–3 次的 2,699 个任务。筛选虽用单一模型-脚手架组合，产出池对另外两个 harness 同样有效；
  • 难度消融（951 任务池 × 4 组）：全带与上半带均提升（post-warmup 验证分 0.671 / 0.670），下半带 0.640，未筛选池无提升——未筛选池中 72.7% 任务永远解不出、13.4% 总是解出，几乎不产生组内差异信号；
  • reward 信息量随时间衰减：8 rollout/任务下「全对或全错」的零方差组占比，OpenHands SDK 从 44.7% 升到 51.4%（全解组增长超过全错组减少）——任务难度是策略相对的，固定池的监督信号会随策略变强而稀释，这解释了为什么需要持续更新任务池；
  • reward 完整性：见 3.4 的六类失败模式表——这些发生率是防御部署前实测的，说明真实训练中 reward 污染是系统性风险而非理论问题。

5.5 可观测与行为分析（§4.5）

  • 故障诊断三案例：① 验证分 0.556→0.150，172 条轨迹仅 60 条到验证——终止分析定位是任务 setup 失败而非策略退化；② 1,024 条轨迹全部单轮终止——轨迹检查发现不兼容的 tool-call parser；③ 崩溃 run（reward 0.351→0.050，turns 18.9→0.96，rollout–训练一致性 0.995→0.851）——轨迹级分析发现「工具调用从输出中消失、命令退化为代码块散文」，据此得到提前 8 步触发的 early-stop 条件；
  • 行为变化（OpenHands SDK，420 轨迹首末对比）：编辑后回读 73.6%→98.1%、首次编辑前探索文件数 3.45→6.92、命令失败后仍解决 63.9%→66.8%、畸形工具调用 1.07%→0.15%、pass@8 覆盖率 83.2%→87.9%、pass8 可靠性 28.3%→39.4%——训练显著改变自检行为（+24.5pp），但对「出错后的恢复」改变有限（+2.9pp）；
  • 交互 horizon 增长：OpenHands SDK 平均 response 43.5k→90.9k token，主要来自轮数 46.6→83.1（+78%）而非单轮长度（+17%）；Claude Code 只到 41k→51k——harness 决定轨迹分布；推理占比（非工具调用字符比例）0.22→0.39（OH）、0.18→0.39（CC），两个 harness 收敛到同一水平，且变难任务收益最大（起点低）——但作者明确说明这是分布漂移观察，不是「推理导致成功」的因果证据。

5.6 系统效率（§4.6）

  • 瓶颈分解（3,699 条 OpenHands SDK trial）：agent 执行占 91.3%（均 840.5s / 总 920.4s），沙箱 setup 2.3%、验证 3.9%，但后两者长尾显著（p99 275s / 928s）——因此分阶段超时而非整 trial 超时；异步下 rollout 槽位空闲率中位数为 0，但 trainer 仍分别等待 40.8%（OH）/ 66.1%（CC）的训练时间——生成是吞吐主瓶颈，优化不是；
  • 同步 vs 异步：同一 7.5 小时内，同步完成 3 步、异步 7 步（步耗时 2.5× 降幅）；校正 GPU 组优化吞吐差异（2.1×）后，同步步耗时估计 2.5→1.9 小时 vs 异步 1.0 小时——结论受 staleness=1 限制，更大 staleness 可进一步重叠；
  • 沙箱优化：懒拉取（1.7× 中位 / 23× 最大冷启动，网络 21.6GB→1.59GB）、预构建镜像 33.2×、挂载运行时 15.4×；判分依赖打包无延迟收益，仅为 reward 可复现性保留。

7. 局限性与开放问题

  • 证据面窄：全部实验用 Qwen3.5-35B-A3B 单模型、每个 harness 单次 run——训练收益与系统效率的 run-to-run 方差未量化；跨模型架构、混合 harness 训练未验证；
  • reward 粒度：二值可执行验证可靠但粗糙，无法给「错误恢复」等行为中间学分；防御覆盖了观察到的失败模式，不保证对所有 reward 利用策略免疫；
  • 保真的边界：训练严格限制在「能精确保留身份与概率」的 token 上，被压缩重写的轨迹直接丢弃——这保证了正确性，但代价是数据效率（丢弃率 2.4–7.1% 只是显式过滤，还有隐式排除）；log-prob 一致性依赖 weights 匹配 + R3，任何引擎侧改动都可能静默破坏（附录 B 的错位重放案例就是教训）；
  • 成本门槛：8×A100/H100 + K8s 集群 + 预构建镜像体系，单 run 生产规模（3 epoch、512 trial/步）的成本使其难以成为可快速迭代的科研工具；异步下 trainer 空闲 40–66% 说明整条链路的算力利用率仍受生成侧主导；
  • 诊断的因果性：行为分析（推理占比、自检、恢复）都是观察性结论，作者明言不构成自动化因果验证；
  • 未来工作（作者自述在推进）：混合任务训练、单策略跨 harness 联合训练、更多 harness 适配器、比终态二值 reward 更细的学分分配、Live UI 自动化诊断。

8. 对我们工作的启示

8.1 与 RTX 4090 / 现有 infra 的差距

诚实地说，Lego-RL 的完整形态在我们现有资源下不可复现：官方门槛 8×A100/H100 + K8s + Nydus 镜像体系；4090 单卡跑不动 35B 稀疏 MoE 的 expert-parallel 推理，partner 的 4×H20 距 demo 规模（8 GPU）也差一半。但它的思路层级与我们的多条研究线直接共振：

  • R3 的「对齐」教训（错位重放把相关性从 0.9993 打到 0.7503 且表面不可见）与我们的 P9→tl.constexpr→CUDA Graph→XLA 批次不变性模式同构：都是「分布式/训练推理之间存在一个必须显式保持的不变量」。R3 可以视为「路由不变性」——我们的 cross-framework 模式列表可以加第 5 条成员；
  • trajectory filter 的「单例 uid」技巧是我们 GRPO 数学工作（组归一化对噪声敏感）的直接工程化：零化 reward + 摘出组统计 + 零化 advantage 三重保险，且 batch 形状不变——这一招完全可移植到我们自己的 verl 实验脚本里；
  • 「训练只吃可精确保留的 token」原则是对我们「GRPO 对 log-prob 敏感」结论的工程回应——宁可丢数据，不可喂噪声；
  • reward 完整性检查清单（git 历史 / 参考修复下载 / 测试文件编辑 / grader 误应用参考 patch）可以直接用于我们 fork 评审和实验设计时的 verifier 审计。

8.2 可行动的后续

  • patch 审阅 → fork PR 机会：Lego-RL 在 verl v0.8.0 上打了 32 文件补丁，其中 trajectory_filter、rollout_corr_helper 的分布指标（p50/90/99 + tail 分数）、DataProto 缺键对齐、KV/prefix 探针接口都是与 agentic RL 解耦的通用改进——可对照上游 verl 现状，评估哪些值得提炼成独立上游 PR（与我们的 verl fork 系列一致）；
  • 把「保真度」验证加入我们的实验规范：论文的 rollout–训练 Pearson 相关性 + |Δlog p| + R3 专家重叠三个指标，成本低、可自动化，适合作为任何 verl 训练的 CI 级检查；
  • 单机降级实验（可选）：BACKEND=docker + 更小模型（如 Qwen3-30B-A3B 或 8B dense）+ 小任务池可以在单机 8 卡上跑通 1/16 demo 流程验证数据流，但训练收益预期远低于论文——适合做工程验证而非科研复现。

9. 结论

Lego-RL 的价值不在于发明新的 RL 算法，而在于把 coding-agent RL 从「demo 阶段」推到「生产可信」的系统性工程答案：用 in-process proxy 在生成时刻捕获 token 级真值（配合 R3 路由重放）解决保真；用沙箱化可执行验证 + 阶段式反作弊 + 终止感知轨迹过滤解决可信；用轨迹级 Live UI + agent plugin 解决可观测。它在三个原生 harness 上的 SWE-bench 提升（+5.8~+9.4 pp）证明「不侵入 agent 也能有效训练」，而 harness 特异的收益曲线则实证了「harness 是优化目标的一部分」这一论文立场的现实意义。对做 RL infra 的我们而言，它的最大启示是：当训练信号（log-prob、路由、reward）不可信时，工程防御（捕获、过滤、诊断）的价值不亚于算法本身——这与我们 GRPO 系列工作中「信号质量决定学习质量」的结论完全一致。
