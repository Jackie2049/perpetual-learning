1 · 研究问题

LLM post-training（RL / 推理类后训练）中，rollout 阶段的性能由什么决定、可以被系统化优化到什么程度？

范围：rollout-native 系统与论文（L1 token 级 → L4 pipeline 级）+ serving→rollout 迁移分析 + 代码实现对照。

明确不做：reward / 算法本身的改进（只关心其对 rollout workload 的影响）、pretraining、纯 serving 部署。

2 · 核心假设：Serving ≠ Rollout

rollout 不是「serving 换个负载」——两者在请求模型、核心指标、版本与正确性约束上系统性不同。每个调研条目都要回答：它隐含的 serving/rollout 假设是什么？反例单独登记。

维度ServingRollout
请求模型独立用户请求，到达不可控一批 trajectory，同批生成、同步/半同步推进
核心指标TTFT / TPOT / latency / goodputtrajectory throughput、rollout makespan、bubble ratio、GPU-hours、RL step time、time-to-quality
版本约束单一模型权重policy 连续更新 → drafter / cache / 调度决策随版本过期（staleness）
正确性约束输出质量policy 版本、同权重训推数值差异、old logp 语义分别核

3 · 性能模型

Trollout ≈ maxi Ttrajectory,i sync RL 下 makespan 由最慢轨迹支配 —— 平均 tokens/s 高 ≠ rollout 快；长尾 / straggler 是 L3 调度类工作的理论起点

4 · 分类法（Taxonomy）

层（L1–L4，允许反例修订）：

层核心问题代表性技术抓手
L4 RL Pipeline Co-designrollout 与其他阶段的协同（例如 train/reward/env/weight-update）sync/async、colocated/disaggregated、overlap、weight sync、staleness、partial rollout、resource allocation
L3 Cluster一批 trajectory set 整体最快（minimize makespan）global scheduling、length prediction、straggler/tail、migration、cache-aware routing、elastic
L2 Engine / Replica一个 engine 高效完成一组 trajectoriescontinuous batching、chunked prefill、prefix/KV reuse、multi-sample、sleep/wake
L1 Token / Model Execution单 token / decode step 怎么更便宜attention/kernel、KV cache、quantization/FP8、speculative decoding、MTP、draft model

类型（第二维度）：

  • A — Make each trajectory cheaper（C(trajectory)↓）：speculative、MTP、KV/prefix reuse…
  • B — Execute the trajectory set better（Schedule({traj_i})）：batching、length-aware scheduling、migration…
  • C — Generate less/better rollout work（改变 {traj_i}，可能改变训练分布，必须单独标记）：early stop、partial rollout、filtering、adaptive allocation、trajectory shaping…

C 类判定原则：按实际改变的训练轨迹集合判断，不按技术名称判断（如 partial rollout 若仅提供路由信号，不自动归 C）。
