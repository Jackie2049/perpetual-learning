**【大白话讲明白】**

AReaL 是一个强化学习后训练框架：模型生成回答、打分、再用这些样本更新模型，反复循环。和之前查过的推理引擎一样，它也有很多"开不开某个功能"的开关。

这一批扫出 42 个函数层面的开关，其中 7 个看起来"有分支、但全代码库没人给它传值"——按以往经验这正是那种"设了没用、也不报错"的毛病。逐条查下来，**7 条里一条都不是**：

- 三条是**按新写法传的值**：代码没有直接调那个函数，而是先写一句 `functools.partial(函数, 开关=...)`，相当于"预先把参数填好"，之后再拿这个半成品去调用。扫描器只认直接调用，所以看不见。**值其实一直在传**，配置也一直是生效的。
- 一条是**开发期调试开关**：MoE 那一层有个"用 CPU 版实现"的开关，CPU 版代码写得完整，但从来没人打开过。不过它不是用户能配的东西（没有命令行、没有配置文件项），更像开发者自己留的后门。
- 两条是**内部默认**：checkpoint 存取时的两个参数（"按分布式格式存"、"连随机数状态一起存"），调用方一律不传、所以恒定为默认值。这是有意为之，不是配置项。
- 最后一条（`use_local_output`）默认值就是设计意图，调用方不传就是走默认。

**这批真正学到的东西是**：训练框架的开关**大多在配置类里**（AReaL 的 `cli_args.py` 有几百个 `field(...)`），而不在函数形参上。所以"扫函数形参"这套办法，在训练侧天然只能看到很小一部分。下一批要系统覆盖得换口径。

**【What–Why–How】**

- **What：** AReaL `3b936798` 快照上，42 个带布尔默认值、在函数体内按它分支的形参里，7 个没有任何直接调用点传值。
- **Why：** 这类开关的危害是"配置看起来生效、实际不影响行为"。推理引擎六批后换到训练侧，检验同一套判据在训练框架上是否仍成立。
- **How：** pyflag 扫出 42/7；逐条用 AST 找**所有**传值形态（关键字、位置实参、`functools.partial` 的第一实参、属性传参）后：4 条在 `partial` 里、1 条确实无人传但非用户面、2 条是内部默认。**边界**：只覆盖函数形参，不覆盖 config dataclass 字段（训练侧的主要形态）；`use_cpu` 只证明"CPU 分支无人打开"，不证明"CPU 实现本身有问题"。

## 三、本批的方法产出（真正值得留下的）

### 1. `functools.partial` 隔了一层

三条 R1 同源。扫描器收集调用点时只看 `ast.Call.func` 的名字是不是目标函数名：

```python
loss_fn = functools.partial(
    grpo_loss_fn,                                 # ← 这里不是 Call.func
    eps_clip=self.config.eps_clip,
    ...
    use_sapo_loss=self.config.use_sapo_loss,      # ← 真正的生产者
    use_cispo_loss=self.config.use_cispo_loss,
    use_decoupled_loss=self.config.use_decoupled_loss,
    ...
)
...
self.engine.train_batch(mb, loss_fn=loss_fn, ...)  # 之后才被调用
```

⇒ **`partial` 的第一个位置实参算一次调用，它的关键字实参算生产者。**
同族还有 `lambda` 与装饰器包装。已写进 pyflag readme 第 4 条，**尚未进扫描器**
（要做就得把 `partial(f, ...)` 展开成一次 `f(...)`，位置实参的对应关系也要跟着重算）。

### 2. 训练侧开关的主要形态不是函数形参

AReaL 的配置面在 `areal/api/cli_args.py`（数百个 `field(...)`），pyflag 由「函数形参默认值」
发现开关，**只能看到函数层面那一小部分**。42 个开关相对它数百个配置字段，覆盖很低。

⇒ 训练侧要系统覆盖，得另做「配置字段 → 消费点」的扫描（字段被声明、有分支读它、却无人赋值），
**不能照搬 pyflag 口径**。这一条比"又扫了一个仓库"更有价值。

## 四、本批两处判据错（都由重跑抓出）

1. **`get_rng_state` 的"唯一调用点"假红**：按名字匹配把 `torch.get_rng_state()`、
   `current_platform.get_rng_state()` 也算成 AReaL 的 `MegatronCheckpointManager.get_rng_state`。
   第一版改成"只要是属性调用就算"——**照样错**，那两个也是属性调用。最终加 `self_only`：
   只收 `self.get_rng_state(...)`。⇒ **同名不同对象按接收者区分，不能按调用形态区分。**
2. **`with_rng: bool = True` 数错**：判据里凭印象写"3 处"，实际 **4 处**。⇒ 判据里的常数必须现数。

## 五、为什么这条不对外

- **R1 四条的开关一直是生效的**（只是扫描器看不见），无需任何上游动作。
- **R2 的 `use_cpu`** 没有配置字段、没有 CLI、无用户面，属开发期调试开关；
  后续批已查完这段回退的行为：**实现本身在上游缓冲口径下是对的**，但 `kernels.py` 顶层依赖
  Triton，缺 Triton 时整模块进不来 ⇒ 结论是「开关不可达 + 实现可用」。见
  [use-cpu-fallback-2026-11](use-cpu-fallback-2026-11.md)。
  真要提，最多是「删掉那个形参和分支」或「给它接个开关」，价值 <3/10。
- **R3 两条**是有意的内部默认。

⇒ **不对外，无待授权的上游动作。**
