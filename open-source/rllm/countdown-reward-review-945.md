**【大白话讲明白】**

Countdown 是这么一种题：给你几个数字，要求每个数字**恰好用一次**、只用加减乘除，凑出目标数。答对了奖励记 1 分，格式对但答案错给 0.1 分。

现在的判分有两处漏：① 它用正则去"数"答案里出现了哪些数字，而小数点会把两个数字粘成一个——答案写 `1.5 * 2`，程序数出来的数字是 `[1, 5, 2]`，正好和题目给的三个数对上，而且结果真等于 3，于是判满分。可 `1.5` 根本不是一个数字，这是把题目给的 1 和 5 改成了一个 1.5。② 它只禁止了"字符表以外的符号"，而 `**`（乘方）和 `//`（整除）都由字符表里的字符组成，同样放行。乘方还带来第二个麻烦：题目给的数字不大，写成指数塔时计算机要算一个天文数字，判分的进程会卡在那里。

有人已经提了 issue 和 PR，PR 的做法是：从字符表里去掉小数点，再显式禁掉 `**` 和 `//`。我按照这个思路在本地重新跑了一遍，既确认了漏洞存在，也确认补丁没有把合法的整数算式误伤——包括 `10 / 4 * 2` 这种中间结果带小数、最终答案是整数的写法。

**【What–Why–How】**

- **What：** `rllm/rewards/countdown_reward.py` 的 `validate_equation` / `evaluate_equation` / `compute_score`（三者在同一文件，见快照 `countdown_reward_main_4e828c8.py`）。范围只限该奖励函数，不涉及 `reward_fn.py` 的其他分支。
- **Why：** `validate_equation` 用 `re.findall(r"\d+", ...)` 取数字，小数点不影响匹配，于是 `1.5` 被读成 `1` 和 `5` 两个数；`evaluate_equation` 的白名单 `^[\d+\-*/().\s]+$` 同时放行 `.`、`**`、`//`。三处叠加即可让违反任务规则的答案拿满分。指数链的问题是 `eval` 对 `a**b**c` 先算 `b**c`，数字一大就必须构造一个位数天文数字的整数。
- **How：** 用快照源码（真实 `compute_score`，`rllm` 导入以最小桩替代）逐条打分，期望值写成常量；再用 `ast` 生成 3–4 个数字的全括号表达式作为"合法答案池"，对其中在 main 上得 1.0 的 22639 条逐条比较补丁前后的分数。**负向对照**：把补丁改成"拒绝一切"，同一搜索必须报出 159 条回归（实测如此），否则搜索本身没有作用。**边界**：未在真实训练里跑过；未测 rLLM 其他奖励函数是否共用同一套数字解析；`44**19**35` 这类"永不返回"的具体时长未复现（值约 10^45 位，跑不完也测不出数），只测了可测的两档耗时。

## 实测结果

### 一、issue #945 的四类答案在 main 上确实拿满分

| 答案 | 题目数字 | 目标 | main 得分 | 说明 |
|---|---|---|---|---|
| `1.5 * 2` | 1, 5, 2 | 3 | **1.0** | 小数点把 1 和 5 粘成一个 |
| `.5 * 8` | 5, 8 | 4 | **1.0** | 同上，前导小数点 |
| `3 ** 2 * 5 - 7` | 3, 2, 5, 7 | 38 | **1.0** | `**` 不在禁止之列 |
| `7 // 2` | 7, 2 | 3 | **1.0** | `//` 不在禁止之列 |
| `(3*2)+(5-7)` | 3, 2, 5, 7 | 4 | 1.0 | 合法对照，也应满分 |

### 二、指数链会拖住判分，但量级要说清

| 答案 | 结果 |
|---|---|
| `44**19**2` | 立即返回（0.0 秒级） |
| `44**19**5` | **2.1 秒**才算完 |
| `44**19**35`（issue 举例） | **未复现**——该值约 10^45 位数字，跑不完；本仓库不把"跑不完"写成测量结果 |

⇒ 支持"一条采样答案可以拖住奖励 worker"，但**不能**说成"必然长期挂死"；指数高度每加一层，成本跳约两个数量级（`**2` 瞬时、`**5` 两秒），到 `**35` 已超出可完成范围。

### 三、PR #946 的补丁没有误伤合法答案

- 补丁就一处：白名单去掉 `.`，并显式 `"**" not in` 且 `"//" not in`。
- 在 **22639 条**于 main 上得 1.0 的合法答案上逐条比较：**补丁后失去满分的 0 条**。
- 其中包含容易踩到的写法：`10 / 4 * 2`（中间值 2.5，最终 5 为整数）、`-1 + 4`（一元负号）、`(4+2)/3`。
- **负向对照**：把补丁改成"拒绝一切"后，同一搜索报出 159 条回归 ⇒ 搜索有分辨力，"0 条"不是空转。

### 四、中途抓到自己两处假通过（写在这里，免得被当成本批可信的默认前提）

1. **第一版回归搜索把 22639 条全报成"零敏感文本"**，因为判断"这段文本会不会被补丁拒绝"时漏了 `**`——先单独用 2 万条随机字符串暴力对照，确认判定式与补丁行为逐条一致后才发现统计口径错，不是判定式错。
2. **第二版把搜索范围收窄成"补丁明面上会拒绝的文本"**，于是负向对照（补丁拒绝一切）报出 0 条回归——**一个连全拒绝都查不出来的搜索，不能用来证明"没有误伤"**。改成对全部 22639 条比较之后，负向对照才报出 159 条。
   ⇒ 判据：**负向对照必须在"被测逻辑明显错误"的强条件下仍能被触发**；"只有预期类别才比较"这种收窄，等于把对照一起关掉。

## 对外判断（本地完成，未发布）

- **issue #945 的技术描述属实**，四类都在真实源码上复现；唯一需要收窄的是"挂死"的说法（见上表）。
- **PR #946 方向正确、未见误伤**。可补的两点（若用户决定参与讨论才发）：
  1. PR 描述里"合法答案前后都得 1.0"给了 5 个例子，但没说覆盖面；本地补跑 22639 条全为 0 回归，可作为补充证据。
  2. 补丁用 `"**" in` / `"//" in` 子串判断，语义上是"文本里出现这两个符号就拒"。对 `/` `/` 分写（`7 / / 2`）这种写法两边都会在 `eval` 阶段报错，行为不受影响；但若将来把白名单改成更宽松的形式，子串判断会与"运算符"语义脱节——属可选建议，非缺陷。
- **未做的判定**：这处漏洞对训练的实际影响有多大（模型是否真的学会写 `1.5*2` 这种答案）没有数据；issue 里那句"policy can learn to score by writing these forms"是合理推断，**未测**。
