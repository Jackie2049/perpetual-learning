**【仓库】** [MLC-LLM](https://github.com/mlc-ai/mlc-llm)（MLC 社区的通用 LLM 部署引擎，靠机器学习编译把模型编到各后端）

**【价值评估】** 3 / 10 — 证据链完整且可复现（`verify_findings.py` 21 checks + 4 条注入全红、`probe_router_chain.py` 8/8），但结论是负的：没有可对外的缺陷。真正留下的东西是扫描器的一处系统误判与它的修法。

**【进展】** 2026-11-05 完成两条扫描与逐条归因，纯静态 + CPU 源码执行（未装 mlc_llm、未建 TVM、未起服务）。**本批有两次自错**：① 探针第一版用字符串替换做反事实注入，同一条字符串命中签名行和调用行，读数反向，一度准备写成缺陷；② `verify_findings.py` 的 `F1c` 用"docstring 之后"切源码，文件里有两段 docstring 时切错位置。两处都由 `--selftest` / 重跑抓出并修正。

**【大白话讲明白】**

MLC-LLM 是一个把大模型编译成各种后端可执行文件的部署引擎，它有一批"开不开某个功能"的布尔开关。有一种不报错、也很难发现的毛病：开关在代码里有声明、也真的按它分支，但全代码库没有任何地方给它传值——那用户设了也白设。我们之前用 pyflag 在六个框架上抓过这类问题，这次换到 MLC-LLM。

这一批的结果是：**没有这种毛病**。看起来最像的两条，最后都查清了——

- `mlc_llm router --enable-prefix-cache`：命令行参数一路传到真正的 `Router` 类，`True` 就让每个子服务端把前缀缓存设成 `radix`，`False` 就设成 `disable`。扫描器说它"没有生产者"，是因为中间那个只是转手的 `serve()` 函数被算成了"用这个开关做决定的人"。
- 编译期的 `enable_disaggregation`：38 个模型里只有 3 个显式把它传下去，其余 35 个吃默认的 `False`。这是设计（按模型接），不是开关坏了。

但这两条候选暴露了扫描器的一个**真问题**：它分不清"自己用这个开关"和"把它转手交给别人"。这个已经改掉了，并且回头用 verl、SkyRL、OpenRLHF 三个历史仓库验证：判定结果一条没变。

**【What–Why–How】**

- **What：** 对象是 MLC-LLM `44fd06d0`（2026-10-30）；问题是那些有消费者、按它分支、但**全仓无写入 / 无传值**的布尔开关（Python 形参）与结构体字段（C++）。
- **Why：** 这类开关的危害是"配置看起来生效、实际不影响行为"，既不报错也不打日志。Python 版 pyflag 已在六个框架上跑过（合计 101 条候选→4 条真缺陷），MLC-LLM 的形态特点是**前端 CLI → interface 工厂 → 引擎类**三段式，中间那段极易被误读成消费者。
- **How：** Python 版扫出 7 个开关 / 2 条候选，C++ 版扫出 22 个字段 / 1 条候选；逐条绑行号归因后真缺陷 0 条。两条 Python 候选的根因相同（工厂转发），已修进扫描器并加单测与三仓库回归；C++ 那条是收敛初始化里用注释写的字段名（TM-018 已记录的第二类写入形态）。**边界**：正则/AST 级分析不做符号解析，报"没人写"仍需人工确认；C++ 版扫 MLC-LLM 信息量天然低（C++ 是服务层，配置面在 Python）。

## 二、两条 Python 候选：工厂函数被当成了决策者

`python/mlc_llm/interface/router.py:17` 的 `serve()` 函数体里没有
`if enable_prefix_cache:`，但这个名字出现在

```python
router = router_type(
    ...
    enable_prefix_cache=enable_prefix_cache,   # :38
    ...
)
```

的**实参位置**。`serve()` 是工厂，决策在 `python/mlc_llm/router/router.py:28` 的形参与
`:86` 的 `prefix_cache_mode="radix" if enable_prefix_cache else "disable"`。

`probe_router_chain.py` 把三处真实源码在 CPU 上跑起来（真 `Router.__init__`（含它的
`start_server` 闭包）、真 `interface.router.serve`、真 argparse 参数表；`tvm_ffi` / `fastapi` /
`uvicorn` / `EngineConfig` / `PopenServer` / `Tokenizer` 用最小替身，清单进读数 `stubs`）：

| 镜头 | `True` | `False` |
|---|---|---|
| C1 两台 `PopenServer` 拿到的 `EngineConfig.prefix_cache_mode` | `radix, radix` | `disable, disable` |
| C2 `Router(...)` 收到的 `enable_prefix_cache` | `True` | `False` |
| C3 argparse 解析结果 | `True` | `False` |

⇒ `verdict: WIRED`。`--selftest` 8/8：删掉转发行 → C2 读成 `<absent>`（两条）；
把三目条件写反 → C1 两档互换。

`enable_tracing` 是同一形状的四跳：`cli/serve.py:181` `--enable-tracing` →
`interface/serve.py:86` → `serve/engine.py` 两个引擎类转给 `super()` →
`serve/engine_base.py:420` `if enable_tracing: self.trace_recorder = EventTraceRecorder()`。

## 三、探针第一版给了反向读数（本批最该记的一条）

第一版探针的基线读数就是**错的**：它对真实 `interface.router.serve` 跑出来
`router_kwargs_enable_prefix_cache = <absent>`（即"CLI 的值没传给 `Router`"），
我据此一度准备把它写成一条真缺陷。

**错在替身，不在源码。** 第一版为了让 `serve()` 跑完，把 `uvicorn` 换成了空模块
（`types.ModuleType("uvicorn")`），而真实 `serve()` 的最后一行是
`uvicorn.run(app, ...)` ⇒ `AttributeError: module 'uvicorn' has no attribute 'run'`，
异常在 `Router` 已经构造完之后、`serve()` 返回之前抛出。这一轮里的 `Router(...)` 其实
是**带关键字的**，可异常让 `serve()` 没法正常返回，探针那一轮被记为失败并从读数里剔除 ⇒
读成 `<absent>`。**读数错在"把异常轮当成了正常轮"，不在源码。**
换上 `uvicorn.run = lambda *a, **k: None` 之后同一份源码读出 `True / False`。

**红灯来自 `--selftest`**：反事实注入（删掉 `Router(...)` 里那个关键字实参）本该让读数
翻转，读数却没动 —— 因为基线本来就是 `<absent>`，"再删一次"当然还是 `<absent>`。
注入是空转的，判据于是"两边都绿"。现在的注入按 AST 定位 `Router(...)` 调用再删实参
（`drop_router_kwarg`），并加了"注入必须真的改动源码"的前置检查。

这和 TM-017 那次 `sed` 事故同类：**判据绿不代表读的是原文件；判据红也不代表源码有问题。**
先怀疑工具。

## 四、扫描器的根因与修法

| 症状 | 根因 | 修法 |
|---|---|---|
| `serve()` 被记成消费者 | 只把 `if` 测试里的名字算成"消费"；名字作为**调用关键字实参**出现时既不算消费也不算转发 | 关键字实参也算消费 → `serve()` 变成"转发型消费者" |
| 转发被当成决策 | 没有区分"自己用"与"交给下一跳" | 形参只被传出去、从不被 `if`/赋值/属性读到的消费者标 `forwarded`，落 `deciding_consumers`，`silently_inert` 只看决策者 |
| 容器键位写入看不见 | 生产者只认关键字/位置实参 | 新增 `container_writes` 字段**只作线索**，不进 `producers_total` |

回归：verl `6879e1ab07`（8 条失效）、SkyRL（7 条）、OpenRLHF（0 条）三份归档的
`silently_inert` **逐条相同**；`test_scan_unwired_flags.py` 16 passed（新增 3 条，其中一条是
反面对照：真在 `if` 里用的消费者不得被标成 forwarded）。

## 五、编译期开关 `enable_disaggregation`：不是运行时开关

`python/mlc_llm/nn/kv_cache.py:41` 的 `enable_disaggregation: bool = False` 会被
`:91` 的 `rx.prim_value(int(enable_disaggregation))` 编进 KV cache 的 TIR。生产者是**模型侧**：

| 显式传 | `llama_model.py:421`、`llama4_model.py:700`、`nemotron_model.py:401`（3 个） |
|---|---|
| 省略（吃默认 `False`） | 其余 **35 个** `PagedKVCache.create_generic` 调用点 |

`compiler_pass/dispatch_kv_cache_creation.py:175-176` 里那两行
`kwargs.pop("enable_disaggregation", False)` / `kwargs["enable_disaggregation"] = ...`
看着像接线，但 `kwargs` 是 `create_tir_paged_kv_cache(self, bb, kwargs)` 的**具名形参**
（不是 `**kwargs`），两行只是同一个字典读出来再写回去。`probe_container_write.py` 5/5 钉住这一点。

⇒ 口径：**这是编译期按模型接的设计，不是"开关坏了"**；未传的 35 个模型走的是显式的默认值。
