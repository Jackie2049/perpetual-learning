# 开源文档撰写规范

<!-- contribution-summary:start -->
**【仓库】** [perpetual-learning](https://github.com/Jackie2049/perpetual-learning)（AI 技术探索与贡献引擎）

**【贡献点】** 统一开源文档抬头，让用户无需询问 Agent 就能读懂工作，并供 GitHub Pages 直接展示。[板块总览](README.md)

**【类型】** 文档规范

**【价值评估】** 8 / 10 — 提高现有成果的可读性与复用效率；格式合格仍不能代替事实核验。

**【进展】** 本规范适用于新增与更新的开源 Markdown，抬头由提交检查及网页构建共同校验。

**【大白话讲明白】**

读者不应先了解一串函数名和 Issue 编号，才能明白我们在做什么。每篇文档先讲清对象、问题、价值与真实进展，详细代码和实验放在后面；网页展示同一份内容，省去反复点链接寻找答案。

**【What–Why–How】**

- **What：** 所有 open-source Markdown 的统一抬头及维护规则。
- **Why：** 旧抬头把执行细节放在结论前，状态混杂且缺少背景，读者只能再询问 Agent。
- **How：** 使用七个固定字段，先写易读解释，再写技术说明；随结论更新抬头，并通过同一解析器供网页展示。

## 适用范围与入口

适用于 `open-source/` 内所有 Markdown：候选、PR/评论草稿、扫描、追踪、目录、规范和交接。目录或规范的“贡献点”写清它解决什么信息组织问题，“类型”可以是项目总览、候选追踪、方法规范等，不伪装成代码修复。

本文件是唯一规范来源；README 负责导航，根 AGENTS 要求执行。将来若做 Skill，也应引用本文件，不复制另一份模板。技术与发布授权仍以根 AGENTS 和用户分工为准。

## 固定格式

一级标题写成容易理解的事项名称，不使用文件名作标题。标题后、正文前放完整抬头；在实际抬头首尾分别放一行 `<!-- contribution-summary:start -->` 与 `<!-- contribution-summary:end -->`，供网页和检查器定位。模板如下：

```markdown
**【仓库】** [项目名](项目地址)（一句话说明项目定位）

**【贡献点】** 具体解决的问题或提出的改进。[Issue / RFC / PR / 源码 / 证据](链接)

**【类型】** 漏洞修复 / 新特性 / 重构 / 文档改进 / 测试改进 / 问题诊断等

**【价值评估】** 7 / 10 — 一句基于证据的理由，说明关键限制。

**【进展】** 用一句话交代真实阶段、结果与下一步；已发布、已合并等结论附链接。

**【大白话讲明白】**

解释必要背景、发生了什么、为何影响用户，以及本项打算或已经做了什么。不要只翻译标题或重复术语。

**【What–Why–How】**

- **What：** 对象、问题和范围。
- **Why：** 机制、原因或提出该工作的动机；推断须标明。
- **How：** 实际或拟议方法、验证与边界，区分已做和计划。
```

What–Why–How 只写 **What、Why、How**，不追加“研究什么、为什么出问题、如何解决”等标签。大白话面向尚无背景的读者；三点技术解释提供准确机制，两部分不要重复抄写。

## 内容质量

- 用户只读抬头，应能说明“在做什么、为什么值得关注、现在知道什么、还有什么未知”。读者仍需问 Agent 才明白，就要重写。
- 仓库必须有项目链接与简短定位。提到具体 Issue、RFC、PR、社区讨论、论文或其他项目时就地附链接；草稿尚无上游编号时明确写未发布，提供草稿或源码入口，不编造链接。
- 贡献点、进展一般各一至两句，大白话通常 80–200 字，What/Why/How 各一至两句。以独立可理解为准，不为字数删掉重要限制。
- 进展分清我方工作与上游状态：他人的修复不能计为我方合并；Issue 关闭不等于 PR 合并；方案备好不等于已实测。
- 明确源码推断、模拟、提取逻辑测试、真实框架实验及完整训练的差别。合并不代表规模化验证；正确性修复不自动等于性能提升。
- 历史文档注明核验日期或历史性质。版式整理时间不是上游状态核验时间；没有重新查询就不能写“目前无人认领”。
- 抬头只保留当前有效结论，不叠加旧状态、星号、划线状态链或内部评分缩写。旧方案与历史修正留正文，重大撤回在抬头明确说明。
- 更新实际结论、验证范围或发布状态时，同步改抬头。技术方案与主机分工不能借格式整改改动。

## 价值评估

统一 **0–10 分 + 一句理由**，作为基于现有证据的主观投入/复用参考，不是实验测量或接受概率。综合影响、证据、可推进性与投入，不用公式制造精度：

| 分数 | 判断参考 |
|---|---|
| 0–2 | 不再独立推进，错误/过期方案或影响很小，仅保留经验 |
| 3–4 | 有学习价值，但已覆盖、窗口关闭或缺乏新增贡献空间 |
| 5–6 | 有合理价值，关键验证、当前适用性或社区空间仍不确定 |
| 7–8 | 价值明确，有较充分依据或可复用成果，仍有重要边界 |
| 9–10 | 高价值且证据与实际产出形成较完整闭环；10 分审慎使用 |

目录和规范按信息组织/复用价值评分，不能与漏洞修复简单排序。存量分数是整改时的主观评估，旧正文评分保留作历史依据。旧 SOP 的“影响×接受度×契合度/成本”属于性价比参考，不转换、不冒充十分制；重新投入需按最新证据重评。

## 网页与检查

GitHub Pages 从 Markdown 抬头直接读取仓库、贡献点、类型、价值、进展、大白话和三点解释。贡献点、进展、大白话直接展示；技术解释可以展开，完整正文可站内阅读。所有记录平铺，不再用“其余几条”隐藏。

执行 `python3 tools/contributions/summary.py` 检查工作区，提交 hook 用 `--staged` 检查实际暂存内容；网页构建检查已提交快照。语法通过不能证明事实正确或表达合格，作者需读者视角复核。

存量 Markdown 均已按本规范整理，新增与更新文档执行同一检查。版式整理不改变既有技术判断、负责人或实验范围。
