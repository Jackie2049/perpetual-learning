## TM-006（verl `tiled_mlp`）— 最推荐

**缺陷**：`actor_rollout_ref.model.tiled_mlp` 有正式配置项、有官方文档（`config.rst:267-273`），
但 `verl/workers/engine/` 下 **10 个引擎目录 grep `tiled_mlp` 全为 0**，唯一生产调用点从不传 `use_tiled_mlp`。

**为什么这条最值得发**：

1. **M5 已在 4090 真机做完冒烟**（2026-11-02），补丁的四条边界全部实证：

   | 场景 | 实测结果 |
   |---|---|
   | FSDP2 + `enabled=True` | 真实 patch 到 MLP 类，前反向跑通，**fp64 数值精确等价** |
   | 不打补丁 | 与 `enabled=False` **逐位相同** |
   | **FSDP1 下开启** | **硬报错**（storage 越界）——不是静默错误 |
   | 默认梯度检查点开启 | **无显存收益**（5.46 GB 不变） |
   | 关掉梯度检查点 | **16.39 → 8.74 GB（−46.7%，4 片饱和）** |

   → 我原先担心的"fsdp1 下可能引入新的静默错误"**已被证伪**：它是硬报错。

2. **不涉及路线分歧**（不像 TM-005 撞上维护者的 MAGI 决策），修复就是 3 行接线。
3. 补丁已就绪（`open-source/verl/patches/tiled-mlp-wiring/`），`patch -p1` 干跑/应用均通过。

**顺带多出的一个可写进 issue 的实用事实**：默认开梯度检查点时 `tiled_mlp` 拿了 0 收益，
关掉才有 −46.7%。这可能比"配置无效"本身更让用户关心。

**若要发**：建议一条 issue，正文 = ①配置与文档在哪 ②10 个引擎目录 grep 为 0 ③真机冒烟的四条边界 ④修复是 3 行。可附 patch。

## TM-009（rLLM `use_async`）— 可发

**缺陷**：`Tool.__call__` 的 docstring 写「If use_async is **None (default)**」，但签名是 `use_async=False`；
且 `has_async` 对**任何子类**恒为 True。

**危害形态比原记录更实际**（我复核时补的）：基类 `async_forward` 体内是 `return self.forward(...)`，
所以只实现同步的工具被误判时**不报错，而是静默返回 coroutine**。

**上游查重**：`async_forward` 0 命中、`use_async` 仅 1 条无关 PR → 无人认领。

**边界**：生产路径不传该参数，**现有训练不受影响**；不主张"训练结果有问题"。
补丁已就绪（`open-source/rllm/patches/use-async-autodetect/`）。

**若要发**：一条独立小 issue + 复现脚本。建议主线写"守卫被测试掩盖"——上游那个测试之所以过，
正是因为缺陷在吞异常。

## TM-005（verl `use_prefix_grouper`）— 谨慎

**缺陷**：引擎侧无人传参 ⇒ 前缀共享不发生；但 `ray_trainer` 仍按它改组级均衡、跳过重排。

**为什么建议谨慎**：上游 #7202 正是修这条，**2026-08-05 关闭且未合并**，维护者原话
「PrefixGrouper has some limitation, we're exploring MAGI attention」。
再提一次"请补接线"大概率被再关。

**若要发**：**不要**写成"请修接线"。可写的落点是「官方示例同时开了互斥的 `use_dynamic_bsz=True`」
——这是文档自相矛盾，不涉及架构选择。
