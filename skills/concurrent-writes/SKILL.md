# 并发写入：同一 checkout 多会话协作的纪律

## 什么时候用

本仓库（perpetual-learning）只维护 `main` 单分支，多个 Agent 会话可能**同时**在同一个
checkout 上工作。出现下面任一信号时读本技能：

- `git status` 里出现不是你改的文件（尤其是 `M ` 已暂存状态的）
- 文件 mtime 是几分钟前，但你没动过它
- rebase / merge 后 `git status` 干净，但**内容变少了**
- 你要提交的文件与别人的实验目录相邻

## 三个反复踩到的坑（各有真实事故）

### 坑 1：`git add` 会顺手带上别人已暂存的内容

**事故**：本会话想提交自己的日记，`git commit` 却把并行会话的 `AGENTS.md`、`queue_tech-miner.md`
和 15:07 那条日记一起带进了提交。

**原因**：别人已经 `git add` 过，索引是共享的。`git commit` 提交的是**整个索引**，不是你刚 add 的那几个文件。

**做法**：
```bash
git status --short          # 先看清哪些是 M(暂存) 哪些是 ' M'(未暂存)
git diff --cached --stat    # 确认暂存区里都是什么
git add <只加自己的文件>
git diff --cached --stat    # 再确认一次
```
若发现混入别人的内容：`git restore --staged <别人的文件>`，**不要** `git checkout` 掉他们的工作区改动。

### 坑 2：`git rebase --skip` 会连带丢掉同一补丁里夹带的其他改动

**事故**（两次）：一次是自己的 §13.38 四份文档被 rebase 重置；一次是并行会话的
`§13.39` changelog 行在两次并发 rebase 中掉了——而实验目录、`§0` 条目、正文、索引行都还在。

**原因**：两个会话同时 rebase 时，一方的补丁与对方的补丁内容重叠，`--skip` 跳过"重复补丁"
时，把该补丁里**夹带的另一处改动**一起丢了。`git status` 是干净的，所以不会报错。

**做法**：
- rebase 完成后不要只看 `git status`，要**按「文件 × 章节」逐项核对内容**（见下文核对脚本）。
- `--skip` 只用于**确认多余**的提交（例如"记录推送失败"这种已过时的提交），且跳过前先看清它的 diff。

### 坑 3：整块取舍冲突会丢掉另一方的实质进展（最危险）

**事故**：解决 `CONTEXT.md` 冲突时整块选了"theirs"，结果丢掉了上游的 M5 第四十九批条目与整节 §13.42。

**原因**：冲突的表格里，**两边的不同行都在更新**——M1 行有我的新批次，M5 行有对方的真机实验。
整块选任一边都会丢另一边。

**做法**：**先判断冲突类型，再选策略**。

| 冲突类型 | 特征 | 正确策略 |
|---|---|---|
| 双方各新增条目 | 两条内容互不覆盖（不同批次号、不同日期） | **都保留**，按时间序排列 |
| 同一字段各自更新 | 同一行/同一键，内容互斥 | 按"谁更新"取舍，并在提交信息里写明取舍理由 |
| 表格中不同行分别更新 | 如 `\| M1 \|` 与 `\| M5 \|` | **按行合并**，不要整块取舍 |

判断方法：看冲突块里**有没有重复的行标签**。有 → 按行合并；全是新增 → 都保留。

### 坑 4：自己的订正被对方的重写覆盖（最隐蔽）

**事故**（2026-11-02）：我订正了 §20.3.5 里一处错误表述（"残差是舍入"→"是计时缺口"），
提交并推送。随后并行会话**基于一个不含该订正的版本**重写了同一节，我的订正消失，
错误表述回到正文。`git status` 干净、`git log` 里我的提交还在——**但内容没了**。

**为什么比坑 3 更隐蔽**：坑 3 会在冲突里停下来问你；这个不会。对方的重写如果
不是在我提交之后做的 rebase，两边就是**并行覆盖**，git 无从判断该保留谁。

**做法**：
1. 提交后、以及每次 pull/rebase 后，**对有争议的段落做定点 grep**，而不是只看文件在不在：
   ```bash
   grep -c "你加的那句独特措辞" notebook/xxx.md    # 变 0 就是被覆盖了
   ```
2. 在关键订正里留**不可误删的标记**，例如"（2026-11-02 订正，已丢失一次，勿删）"——
   下次被覆盖时能立刻认出这是被删的而不是自然演化掉的。
3. 发现被覆盖：**重贴订正，并在提交信息里写明"重贴"**，让对方看到这里有并行冲突，
   而不是默默再改一遍又可能被覆盖。

**根本局限**：本仓库没有锁、没有分段所有权约定，这类覆盖**无法靠 git 自动避免**。
只能靠"关键结论留标记 + 定期定点 grep"。

## 标准作业顺序

```bash
# 1. 开工前：确认现场（不 rebase，只 fetch）
git fetch origin
git log --oneline -1 origin/main      # 远端到哪了
git status --short                    # 有没有别人在写
ls -lat <要改的目录> | head -3        # mtime 判断是否有人在活跃写

# 2. 有人在活跃写同一批文件 → 换工作，不要争抢
#    （改写文档/实验目录这类共享文件时尤其明显）

# 3. 收尾：只暂存自己的文件，逐项确认来源
git add <自己的文件>
git diff --cached --stat

# 4. 推送前若远端已前进，rebase 并逐轮解决冲突
git rebase origin/main
# 每轮冲突都回到第 3 步的判断：新增条目 → 都保留；同行更新 → 择一并说明

# 5. rebase 后强制核对（关键，见下）
```

## rebase 后的核对脚本

不要靠眼看。用计数对比"rebase 前应有"与"rebase 后实有"：

```bash
# 关键标识逐项计数，任何一项变 0 或变少都要查
for k in "§13.44" "§13.45" "§21.13" "第四十九批" "第五十一批"; do
  printf "%-12s %s\n" "$k" "$(grep -c "$k" notebook/rollout-performance-research.md)"
done

# 别人的产物还能不能跑
cd experiments/<别人的目录> && python3 -m unittest test_xxx 2>&1 | tail -2
```

**判定标准**：不只数"有没有"，还要数**有没有变少**。丢了 1 处和一处在 100 行里，计数上一样不起眼。

## 边界与已知局限

- 本技能针对**同一 checkout 多会话**；不同 checkout（worktree）之间没有这个问题。
- 无法完全避免竞态：本仓库没有强制锁机制，靠的是"先探查、后动手"。
- 计数核对只能发现"丢了"，不能发现"改错了"——语义正确性仍需人读。
- 若两个会话改的是**同一段落**（而非不同行），自动合并可能静默选一方，计数也可能不变。这种情况只能靠读 diff。
