# 结论自查：9 道检查

## 什么时候用

你要写下任何一个下面这样的句子之前：

- "X 比 Y 快 1.5 倍" / "这个开关不生效" / "该机制成立"
- "重建精确" / "误差 < 1%" / "两者不可分"
- "这是最坏情况" / "已接近上界"

**不需要用的时候**：纯记录、纯导航、复述别人的结论。

## 五道检查

### 1. 分子分母是不是同一个东西

**案例（2026-11-02）**：初版把"每块 8 组"除以"每块 32 组"当成基准偏差，实际两者的块结构不同
（一个是完整组、一个把组摊开），比值里 81% 是结构差不是效应。修正后结论从 1.0508 变成 1.0462。

**问法**：这两个数各自的分母是什么？分母是同一批对象、同一时间窗、同一 GPU 集合吗？

### 2. 我在用结论证明结论吗

**案例**：把"判定里写了 evidence 字段"当作"可判定"，于是 11 个块全被判成最高级——
判据读的是自己的输出，不是证据。修正为核对证据锚点是否命中后，才识别出两个降级块。

**案例二**：让墙钟读数按假设的参数调整，于是速度比恒等于公式。

**问法**：这个判定如果换成"没有效应"的数据，还会给出同样的结论吗？换一批输入重跑一次。

### 3. 识别性检验做了吗

**案例**：某指标对"组难度方差"零敏感（方差 0→25，读数极差 0.0），却被当成有效证据用了两批，
之后才撤回。

**问法**：这个指标对我声称它在量的东西敏感吗？对**不该敏感**的东西是否也动了？
两端都要测：① 恒常数输入 → 应判零敏感；② 已知强效应输入 → 应判敏感。

### 4. "小"是不是就等于"可忽略"

**案例（同日两次）**：把"阶段和与整步残差 0.040–0.076s（0.3–0.5%）"当成舍入误差而接受。
实际那是 0.28% 的**计时缺口**，会把份额分母搞错、造出 0.22%／0.51% 的系统伪偏移。
而"残差要查来源"这条，自己在同一天的 §21.9 里刚论证过。

**问法**：这个小数是被测量出来的，还是被构造/假设出来的？**它的来源查了吗？**
0.3% 在性能测量里既可能是舍入，也可能是可归因的系统项——两者处理方式完全不同。

### 5. 我的对照真的能推翻我吗

**案例**：初版拿"两条轨迹逐 tick 取 min"当并集，得到 ratio 0.93，读成"不可加"；
实际是这个合并方式本身放大了并集。正确的对照应当让"若命题为真则 ratio 恰为 1"。

**案例二**：某个"错误做法"的对照跑出 0 误差——**误差恒为零的对照不是对照**。

**问法**：如果我的主张是错的，这个对照会显示什么？如果它无论主张真假都给出同样结果，
那就不是对照。


### 6. 订正有没有传到所有引用点

**案例（2026-11-02，一天内两次）**：订正了「RTX 4090 无 FP8」，只改了 P-2 那一行，
但同一句话在**另外 3 处**还在（§18 第 10 章表、§20.3.5 的缺口表、§20.4 残留）。
更早的例子：`vllm-v0.23-rtx4090-impact-reading.md` §4 当时已经纠过一次，但准确表述没传播开，
简化版继续被约 30 个文件引用。

**问法**：改完之后，`grep` 一遍原表述——**还有几处**？每一处都在哪？

```bash
grep -rn "原表述的关键短语" notebook/ | cut -c1-120
```

**判据**：不是"我改了"，是"**原表述在仓库里不再作为当前结论出现**"。剩下的命中只能是
① 订正记录里对旧址的引述、② 历史日志。出现第三类就是没改完。

**为什么容易漏**：订正时注意力在同一段文字上，而同一结论常被抄进汇总表、章节表、交接清单。
**这些"二手引用"才是传播主力**——源头改了，二手没改，等于没改。


### 7. 核对别人的数字时，我也可能算错

**案例（2026-11-03）**：给归档核验脚本加一条检查时，从归档里只取了 `i3p200` 和 `i3p010`
两条跑，算出整步变化 **−2.98%**，与主文档的 **−4.5%** 对不上，一度判定"发现不一致"。

实际归档有**四条跑**（每臂两条），用两臂完整均值重算是 **−4.54%**——主文档是对的。

**问法**：我拿来核对的样本，和对方声称用的是同一批吗？

**为什么特别危险**：核对动作自带"我在找错"的心理预设，一旦算出不一样的数字，很容易直接
宣布发现错误。**核对者犯第 1 条（分母）的错，会制造一个不存在的缺陷**——比漏掉缺陷更糟，
因为它会浪费别人时间去查一个假问题。

**做法**：核对前先花 30 秒确认 ① 归档里有几条记录 ② 主文档用的是哪几条 ③ 有没有"每臂多跑取均值"这类聚合。


### 8. 核验工具本身会不会骗人

**案例（2026-11-03）**：用 GitHub Contents API 核验推送是否成功，返回 `size: 1516668`，
但解码出的内容是空串——于是判定"主文档的订正没推上去"，甚至开始分析"API 推送丢了中间提交"。

实际是 **Contents API 对 >1MB 的文件不返回 content**。换 Blob API 后，远端与本地
**md5 完全相同**（`8d23033e…`），订正都在。

**问法**：这个"异常"是数据的问题，还是我用的工具/接口的问题？

**特别危险**：即将宣布"内容丢失"这类严重结论时，**先换一种方式复核一遍**。
工具返回的"空"不等于"没有"——可能是它不给你。同样，"查不到"不等于"不存在"。

**做法**：比对**哈希**（`git hash-object`）比比对内容更可靠，且不受 API 的返回策略影响。


### 9. 检查器自己有没有在空转

**案例（2026-11-03，我写的工具里）**：给 `verify_anchors.py` 加"负载来源"检查时，
读的是 `arm['intra_group_cv']`，而归档里**从来没有这个键**（真正的键是
`structure['cv_within_pooled']`）。于是 `cv` 恒为 `None`，那段判据**从未执行**——
但检查一直报 OK。是并行会话发现的。

**这比"检查不到"更糟**：它给出**虚假的安全感**。你会以为这类问题已被覆盖，
实际上那一半什么也没核。

**问法**：我这个检查，在"数据有问题"时真的会报吗？

**做法（三条，缺一不可）**：

1. **查键存在**：读归档字段前先确认键在；缺失要报出来，不能默默当 None。
   ```python
   v = d.get('a', {}).get('b')
   if v is None:
       bad.append({'what': '缺字段', 'got': '键不存在'})   # 不能写成 if v and ...
   ```
2. **负向对照**：故意把输入改坏，看检查会不会报。只报 OK 的检查说明不了任何事。
3. **数一数实际判据条数**：`if v is not None:` 这种守卫会让整段静默跳过。
   跑一次统计"真正执行了的分支数"，别只看总体报 OK。

**一般化**：这是第四次"工具本身骗人"（前三次：只取两条跑、两套放置、API 返回空）。
共同点——**工具的输出不等于事实，必须验证工具自己**。

## 边界

- 这是**启发式清单，不是保证**。它覆盖本仓库一天内 20 条自查记录的主要形态，不覆盖全部错误类型。
- 第 3 条需要构造输入，成本较高；只在"这个指标将来会被反复引用"时才值得做。
- 清单不能替代复现：最有效的仍是**换一批输入重跑**，而不是对着自己的结论想。
