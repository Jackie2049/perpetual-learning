# 工作日志

按日期记录 perpetual-learning 的实际工作过程。当前工作与下一步统一见 [CONTEXT.md](../CONTEXT.md)，项目总览见 [README.md](../README.md)。

## 记录方式

日志是给人读的工作日报，不是给下一个 Agent 的审计凭据，也不是专项文档的副本。读的人应当在两三分钟内知道：这一天在推进什么、每条做成了什么、哪里被推翻、下一步卡在哪。

**文件与时间**

- 每天一个 `YYYY-MM-DD.md`，标题 `# YYYY-MM-DD 工作日志`。每项实际工作在完成、受阻或终止时留下记录，与成果在同次收尾检查并提交；没有独立成果的学习、调研和失败尝试也记录。
- 文件开头用一到两句话说明今天在推进什么，不复述各条结论，不设重复的「当日回看」段。
- 条目用 `## HH:MM — 结论式标题`：标题写「做成了什么」，不写批次号、轮次号或内部编号（章节号可放末尾括号）。
- 时间按真实系统时间取，不能按轮次或调度间隔推算；跨零点使用新日期并同步索引。
- 同一工作的后续进展补充在原条目下，不新开条目；跨日接续在新日志里用一句「接 X 日」说明。

**单条结构**（目标 600–1,500 字节）

1. 背景与目的：1–3 句，说明缺口、触发点或为什么要做。
2. 做法：1–3 句，讲清设置、比较口径和参照点；不逐项复述参数与源码路径。
3. 关键结论：3–5 条 bullet，每条一句，带能记住的关键数字。
4. 材料：一行链接到笔记、实验目录或主文档章节。

**应当写**

- 结论、关键数字、机制解释，以及被推翻的判断（写明「撤回」「推翻」，并给出新结论）。
- 这一批与上一批、下一步的因果关系。
- 影响后续判断的口径问题（如参照点不可达、指标零敏感）。
- 一条可复用的经验即可，不逐条罗列自查过程。

**不要写**（这些属于专项文档、实验 readme 或交接文档）

- 验证范围与合规声明（未跑 GPU、未触上游、身份计数不变、未新计深读）。
- 自查修正的逐条清单与失败尝试的每一步。
- 环境与外部状态快照：GPU 占用、磁盘余量、VPN、上游仓库版本、PR 状态。
- 并发会话的操作流水，除非它直接导致某次结果作废。
- 参数、函数、行号的逐项复述。

**例行核对**

不单独成条。只有状态发生变化且影响当前工作时记一行，无变化不记。机器与上游状态由交接文档维护。

**数量预算**

- 单条正文软上限 1,500 字节、硬上限 4,000 字节：超过软上限时提交检查提示，超过硬上限拒绝提交，说明细节应移入专项文档。
- 单个日期文件软上限 40 KB；一天有多项工作时只保留有结论的，例行与重复工作合并成一行。

**其他**

- 补记注明何时补、依据哪个提交或实验记录；仅能确定提交时间时明确标注。校正错误时间保留原值与依据，未知执行时间不猜测。
- 日志保留当时的上下文和判断；后续纠正补充新记录，文件迁移时可以修正链接。
- 详细成果维护在所属板块，日志通过链接引用；不要把全过程再次复制进 CONTEXT.md。
- 旧日志中的外部状态、机器状态和验证结论按记录日期理解，使用前按需核实。

**历史日志迁移**

按新格式重写旧日志时，先把原文整份存入 `diary/archive/YYYY-MM-DD.md`，再重写当日文件，两者在同一次提交里暂存。提交检查会逐条比对：被移走的每个 `时间 — 标题` 必须在归档中逐字存在，否则拒绝提交。归档文件不进「已有日志」索引，只作为原文留存；用 `git show` 或直接打开可查。

## 工作收尾入口

日志是工作完成的一部分，不是可选的事后总结。按“保存成果 → 写日志 → 按需更新 CONTEXT／队列 → 检查提交”收尾，记录这一条做成了什么、在哪里受阻、材料在哪里。

[日志收尾工具](../tools/diary/readme.md) 自动取时、维护日期索引；启用本地 Git 提交检查后，缺少相应记录的提交会被拦截。语义是否完整、技术结论是否可信仍需 Agent 核对；中断后先据实补记，再继续下一项工作。
