## 当日回看（依赖名册批 + 运行时批）

- **"依赖在不在"和"它在不在路径上"是两个问题（04:07）**：前几轮把每个会在窗口里炸的前提逐个收口，却没人问过清单里的条目**是不是真在这条执行路径上**。`trl` 被当成硬依赖挂了六轮，实际它只在一条永不执行的回退分支里被 import。⇒ 凡是"缺了就中止"的门槛，都要能指出**哪一行代码会用到它**；指不出来的项，不是保护而是风险——它会在真正要用的东西被清掉时，把一个好窗口一起判死。
- **查表式的"分支判断"容易反直觉（同批）**：直觉是"用 causal-LM 权重去建 token-classification 模型应该报错"，实际 `_get_model_class` 只查一次映射、`architectures` 仅用于在候选列表里挑一个，于是它静默随机初始化一个新头。⇒ 判断"走哪条分支"不能凭类型学直觉，要读解析函数本身；这次读出来还顺带纠正了材料口径（critic 的 value 头是从零训练的 1 维头，不是预训练 value model）。
- **未知时的默认值就是风险偏好（同批）**：探针在"读不到映射"时返回"不可判定"，wrapper 对不可判定**沿用旧严格规则**。这不是保守的修辞——本机装不上 transformers 5.16.1，real-mapping 分支第一次执行就在服务器上，所以失败方向只能是"多中止一次"，不能是"静默换错分支"。⇒ 任何"第一次执行就发生在稀缺资源上"的判据，都要显式写出它失败时倒向哪边。
- **新增一个报告字段不等于改判定（同批）**：`valuehead_branch` 只进 reported、不进 V/P 门槛，并且用两条自检钉住"缺失 → 仍 exit 0""改成 `trl_valuehead` → 仍 exit 0"。预登记一旦发布，后续加固只能加**证据**，不能顺手把门槛也挪一格。
- **"自检通过"的覆盖面取决于跑自检的机器（05:12）**：同一份探针在本机（无 `transformers`）5/5 全绿，在装了 `transformers` 的机器上直接 `ValueError` 崩——被 skip 的那三行恰好是唯一没被执行、也没被格式校验覆盖的分支。⇒ 有条件跳过的自检分支，要么在装有该依赖的环境里再跑一遍，要么把 SKIP 明写成"未验证"，别把它算进通过数。
- **预检只 stat 目录等于没验依赖（同批）**：msprobe 目录还在、包被清一半时 `-e` 放行，错误要到第一个训练步（模型加载之后）才出现。⇒ 硬依赖的预检要真 import 一次；这条就是把上一轮 trl 的教训用在同一份清单的另一项上——**同一类错误会换一个依赖再犯一次**。
- **兜底错误可能指向错误的包（同批）**：不打 sdpa 补丁时 FA2 的 `ImportError` 被 `except BaseException` 吞掉，最后报的是"please install trl"。⇒ 宽泛 except 后面的兜底消息必须带上原始异常类型，否则它会把根因改写成另一个包的缺失。
- **本机缺依赖不等于验不了（同批）**：python-build-standalone＋一次性 venv 就能在没有系统 Python 3.10+ 的机器上跑 pinned 版本；`github.com:443` 断时，走 `api.github.com` 的 release-asset 端点（`Accept: application/octet-stream`）仍能下载发布物。
- **"上游默认值没变"不等于"实验没变"（06:09）**：`enable_chunked_prefill` 在 `24f25b03` 与 `31cfccb4` 上默认都是 True、yaml 也都是 true，单看"默认值有没有动"会判无事；真正动的是 **base recipe 里那条显式 `=False`**（`24f25b03→31cfccb4` 的唯一一行差异），它把生效值从 False 抬回 True。⇒ 比对实验条件要盯**最终 argv**，不能只盯 config 默认值——中间的 recipe/wrapper 就是能把默认值覆盖掉的那一层，也是漂移最常发生的地方。
- **配置面回读全绿也可能是错的（同批）**：本臂 `max_num_batched_tokens` 两档都回读 8192，看上去"没变化"；但 verl 里唯一读 `enable_chunked_prefill` 的分支（`_validate_configs` 抬 `max_num_batched_tokens`）在本臂恰好不成立（8192>2048）⇒ **配置面看不到差别，差别在引擎手里**。⇒ 一个开关"有没有消费者"要分两层问：verl 内部谁读它、传给引擎后引擎怎么解释；只看第一层会得出"空转"的错结论（这正是 vLLM V1 那类"反正总开着"直觉容易踩的坑，本轮读源码否掉了它）。
- **检查脚本不能重抄被检查的对象（同批）**：第一版 `preflight-g4.py` 把 wrapper 的 override 表抄进常量里，于是"检查通过"只证明两份手抄件一致。改成桩 `python3` 让 wrapper→recipe **打印真实 argv** 之后，env 层（19 个变量有没有被 recipe 消费）和 override 层同时被覆盖，wrapper 成为唯一来源。⇒ 凡是"核对两份配置是否一致"的需求，先问能不能让生产侧自己输出，而不是复制一份到检查侧。
- **替换 shell 首行可能改掉整条命令（同批）**：为绕开 bash 3.2 的空数组问题把 `set -xeuo pipefail` 写成 `set -xe pipefail`，`set` 把 `pipefail` 当成**位置参数**、覆盖了脚本的 `$@`，10 条尾部 override 全部消失，捕获从 58 条掉到 48 条。⇒ 对"跑的是不是同一个东西"这类检查，**计数本身就是判据**；这类自伤必须进自检（现为 `eaten_tail_detected`），否则它只会表现为一个偏小的数字，看起来同样"通过"。
- **自检注入要打在受检键上（同批）**：把注入写在 `rollout.n` 而受检键是 `actor_rollout_ref.rollout.n`，于是"值被改要报红"这条判据**一次都没被触发**却报绿。⇒ 自检的注入必须与判据读的键是同一个字符串；这与 10-23 那条"注入要绑到具体 check"是同一条纪律的第二次复现，说明它需要机械化而不是靠记性。

## 06:09 — M5 无卡轮：4 卡 inflight=1 臂的开窗前检查——base recipe 少了一个钉

**目的。** critic 三臂已连续五轮只能做无卡准备；TM-008 只剩 4 卡 `inflight=1` 没测（要 4 张空闲卡），而它针对 `24f25b03` 准备、main 已到 `31cfccb4`。核对它还是不是同一个实验。

**自错三处（详见 README）。** `set -xe pipefail` 把 `pipefail` 当位置参数、覆盖 `$@`，吃掉 10 条尾部 override（58→48，已进自检）；自检注入键写成 `rollout.n` 而非受检键，判据未被覆盖却报绿；`+` 前缀检查拿 `key` 比 `key=value` 列表 ⇒ 双向误报。
