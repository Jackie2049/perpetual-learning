## 00:27 — 拆 GRPO 组的代价与收益首次量化：组完整性保的是跨组可比，分组税取决于积压深度（§13.30）

**目的**：补 §15 Q5／§11.2 条目 7 的领域空白——语料内所有 L3 长度调度都以「组不可拆散」为前提，但**没有任何一篇量化「若允许拆组能多回收多少气泡、代价是多少」**。本批给出首次读数。

**做法**：新增实验 `experiments/rollout-group-split-tradeoff/`，三层模型。L1 用解析（χ² 近似）＋bootstrap 仿真量拆组后的归一化统计量与排序翻转；L2 用 FIFO 连续排程量「分组税」（同 workload、同容量下整组原子归还 vs 逐条归还的 makespan 差）；L3 把两侧放进同一判据。GRPO 组内归一化按 verl `core_algos.py:306-321` 与 OpenRLHF `experience_maker.py:256` 读源码固定。

**结果**：
1. **组完整性保护的不是「组内比较」，是「跨组可比」。**组内归一化把优势除以本组标准差（同一常数缩放），所以组内两两排序在任何拆分下都不变（翻转 0）；真正被打散的是跨组尺度——p=2 时 32.8%、p=4 时 49.3% 的跨组排序被读反。这修正了一个直觉表述。
2. **σ̂ 方差膨胀仿真 1.88×（p=2）／3.05×（p=4），恒低于 χ² 解析界 2.33／7.00**——分片共享同一组均值，共同项压缩了方差。故解析界只能作上界，引用须报仿真值。n=4 拆 4 片（每片 1 条）样本标准差未定义，属定义域外，不作数字。
3. **分组税无积压时恰为 0**，4 批积压 43.7%、16 批 54.7%；组内离散度 cv 0.2→1.5 时 20.6%→56.6%；组大小 n 2→8 时 27.7%→43.7%。**无积压为 0 与 §14 候选 D 的实测 1.000 是同一事实**，已在 `consistency_with_candidate_d` 一栏复算确认——两套模型不矛盾，量的是同一件事的两个侧面。
4. **判据「税 > 信噪比损失（p=2 为 27.1%）」两侧都跨得很大，判决是「逐负载判断」**而非单一结论。**积压深度是语料内无人报过的量**，所以「拆组能省多少」在现有报道口径下只能给条件式答案——这是回答本题的新口径要求。

**自查修正（四处，都是先跑出看着合理的数字再推翻）**：① 组臂只跑 `max(g)`、轨迹臂跑全部 n 条，等于给轨迹臂多算 n 倍工作，量化出的收益纯属口径错误；② `_makespan` 在无 pending 时把 `now` 推到全部结束，吃掉轨迹调度优势、税恒为 0；③ 「伪零方差率」把 n=4/p=4 算成 100%，实为样本标准差定义域外；④ 「组内排序翻转率」恒为 ~50%，因为把组内与跨组归一化混在一个指标里，量出的是随机数。①②由手工追踪两档长度小例（`[[1,1,1,1],[9,9,9,9]]`）发现，③④由单元测试的语义检查抓出；四条均已写成测试（13 个通过）。

**验证范围**：进程内解析＋仿真（CPU、仅标准库）；`--verify` 连跑两次通过、13 个单测通过；**未跑 GPU／引擎、未触上游写操作、未新增文献身份（126 身份与 20/84/21/1 族分布不变）、未新计深读**。**边界**：分组税是上界（假设后续轨迹随时可接、无 KV 搬运与跨批版本一致性成本）；积压批数为构造参数；L1 奖励模型为高斯近似。不支持「某系统应该／不应该拆组」，只支持「两侧各有多大、调度侧的答案取决于积压深度」。

- **PP 微批边界与「能不能补上」（M1 12:13）**：§13.34 把上一批的「PP 微批边界」残留做掉了，但它自己留下两句容易被误读的话——「micro-batch 层 81.3% 的组被切开」和「前缀块 3.62×」，合起来像「有个 bug，把 `force_group_size` 接上就能修」。本轮先核源码路径：**这个开关在引擎入口能核到的所有训练路径上恒为默认 1**（`update_actor` 注入的五个默认键里没有它、ray trainer 零命中、五个后端都走没有该形参的 `prepare_micro_batches`）。真正值钱的发现是第二层：**§13.34 的 1.00× 参照点本身就不可达**——它要求一个 micro-batch 装下整批，而训练是按 mini-batch 迭代的。换成可达上限后，能动的只有 **0.47 倍**（区间 0.162–1.000，预算宽松时为零），剩下 1.44× 是「按 mini-batch 迭代」这件事本身的价格。第三层是接线要付的结构账：组完整把批数上限从样本数压到组数，vPP=3 时 `roundup(8,3)=9` 直接触发 `assert num_micro_batches <= num_groups`，vPP=2 下批数只有逐条的 0.42、不均衡从 8.9% 涨到 17.0%。**教训**：写「×倍开销」时必须同时写清分母是哪个参照点、以及那个参照点是否可达；否则一个正确的计数会被后续轮次读成「可修的性能缺陷」，而这个误读正是我自己上一批埋下的。三参照点混用分母是本轮最危险的自查项——第一版就是这么写的，跑出来 3.69 与 1.44 两个数看着都合理，只有一个单测（「上限÷外参照 = 每 mini-batch 组数」）能把它们区分开。**仍然开着**：ray trainer 侧的接线未核到；PP 气泡本身仍未测；可达上限沿用「碎片不共享」的上界假设。

- **M5 算力侧候选 F：结构杠杆零效应（M5 11:17）**：Phase 3 起专项归 M1，本条只记算力侧。同栈 verl 24f25b03＋Qwen2.5-1.5B 单 4090，`ppo_mini_batch_size` 8／16／32（=4／2／1 个优化步/迭代，每迭代 128 samples、micro=1 不变）整步 27.447／27.372／27.374s＝1.0013／1.0041／1.0040×（±0.4% 内，成对差 ≤+0.28%±0.36%）；token 归一化 update_actor 恒 0.316–0.318 s/kTok、每优化步成本≈4:2:1 → **结构切分不改变计算量，不是整步性能杠杆**；效应只在优化轨迹（step-15 acc 0.1333/0.1500/0.2167，单 seed 仅方向）；f16 与基线跨进程复测 −0.41%＝同栈锚点第三次独立基线。数据由 2026-10-31 并行会话跑完三模式后中断，本批取回 f1/f2、md5 三方一致并独立核验立账。

- **M5 算力侧候选 G：多卡强扩展，加卡收益快速衰减（M5 13:01）**：本轮没有自己跑 GPU，而是给另一个 M5 会话刚跑完的候选 G 做独立核验与立账——这本身就是本轮最该记的纪律：**同一台机器上两个会话同时在跑时，scaling 实验对并行负载极敏感，唯一正确的做法是全程不启动 GPU 作业、只做只读跟踪**（g1 03:39 起跑、g2 首试失败、g2 改用 0,1、g4 用 0,1,3,4，我全程只读日志与 md5）。读数：固定 128 samples/迭代、只改 1／2／4 卡，整步 **27.531／22.009／16.878s＝1.251／1.631×**（并行效率 **0.626／0.408**）。最容易漏看的是 **update_weights**：它随 rollout 引擎数变慢（1.82→2.35→2.64s），是唯一负扩展的阶段——单卡只占 6.6%，多卡会持续放大，把「L4 权重同步」与「L2 引擎数量」耦合成了一个同栈可测的代价。另一条是 update_actor：占整步 48.2%，4 卡只到 1.628×，进一步印证候选 E/F 的结论——**阶段占比不能外推 G，会计上界既不能由杠杆兑现、也不能由加卡兑现**。**三条可复用教训**：① 并行会话在跑实验时，「什么也不做」就是正确的实验纪律，抢跑只会污染两边的测量；② verl 的 `perf/throughput` 是**每 GPU 归一**值（g2 的 954.1 是总量的一半），不核实就会把聚合吞吐读反；③ NCCL 的 CUDA 217「peer access is not supported」不一定缺 P2P——本机是 `RAY_EXPERIMENTAL_NOSET_CUDA_VISIBLE_DEVICES=1` 下 Ray 的物理 GPU id 与 `CUDA_VISIBLE_DEVICES` 掩码序号错位，补一个 id→序号映射即可；④ 归档解析脚本的模式标签要从文件名末尾取，别让 `rollout-g8` 里的 `g8` 把 `g1/g2/g4` 覆盖成一个。**仍然开着**：NUMA 未受控（g4 跨 NUMA），分离需在 4,5,6,7 上重跑；P-1 跨系统横评仍待用户立项。
- **`force_group_size` 没有生产者（M1 13:10）**：12:13 那批留了一句「ray trainer 侧的接线未核到，不作全局保证」，读起来像「还有条路径可能把开关打开了」。本轮没去找那条路径，而是换了个更强的命题：**整个 checkout 的非测试代码里到底有没有写入方**。答案是没有——生产代码零命中，唯一写入方是 `test_prepare_micro_batches_with_group_size.py:64` 构造的假输入，也就是说这个特性目前唯一的使用者是它自己的单测。三条看起来能写入的旁路也逐条堵死：三处 `default_keys` 全是静态字面量；TransferQueue 回写确实是唯一能把键带进后续 batch 的通道（`@register` 全部套了 `tqbridge`），但 `train_mini_batch` 只回 `metrics`，通道断在源头；`EngineConfig` 根本没有这个字段，yaml 里无处可配。读引入史才明白成因：`80eb57ea`（#5438）原本是 `assert force_group_size == 1` 禁止它在 dynamic bsz 下用的，那次改动**只是删掉断言并把参数传下去**——只加能力、没加生产者。**教训**：「某条路径没核到」这种残留写法很危险，它把「已知范围内的结论」和「未知范围的可能」混在一起，让后续每一轮都得重新掂量；正确做法是把命题改写成能被证据一锤定音的形态。另外三条自查都值得记：写入方正则第一版漏了 kwargs 写法（恰好就是默认键注入的那种形式，漏掉会系统性放过真正的风险点），是负向对照抓出来的；`lru_cache` 让「注入写入方后判决应该翻成 false」这个正向可行性检验**假通过**，我差点就拿着它当证据；root 不存在时脚本静默返回空集合，把「没扫到」读成了「没有」。**仍然开着**：PP 气泡本身仍未测（并行会话在做）；「组内连续排列」基准的方差低估偏差未修正。
- **mini-batch 组成基准的估计偏差（M1 13:56）**：13:10 那批划掉了 `force_group_size` 的残留，同时留着「组内连续排列基准的方差低估偏差未修正」。本轮去收这一条，原本的预期是「偏差大概 1–2%，顺手核一下」。**结果偏差本身按预期变小、但顺着它查出了比偏差更重要的东西**：§13.32 的 1.0508 不是「同一个块的两种排列」，而是**分子分母的块结构根本不同**——长度全同时 `grouped`（分母）每块装 8 个完整组，而真实 LDM（分子）在权重全等时堆状态完全对称，分区下标是 `(0,4,8,…)`，把 32 个组摊到全部 4 块、**没有一组是完整的**。所以那 5.08% 里 4.12% 只是「分母被压低」而只能归给比值，真正属于「同组被摊开」的只有 0.93%。换到真实长度结构（同 prompt 的 n 条响应长度相关，LDM 反而会把同组摊到各块、块内 29.8/32 个组），读数是 1.0462，其中 98% 才是真实组成效应——**这时 §13.32「真实路径已接近最坏组成」才第一次是定量成立的**。**教训（三条）**：① **「基准有偏」这种话必须先问「偏哪个方向」**。我第一版写的是无条件「组内连续排列把方差读小」，但两层结构下 ρ=0 时它其实读**大**（1.0119），交叉点在 ρ≈0.12——机制解释如果不对机制本身取条件，就会变成一段看起来很有道理的错话。② **「构造档」和「真实档」不是同一个反事实**。长度全同的对照组是我为了复现 §13.32 才加的，它给出的 1.0508 看起来「和原文一致」很让人安心，但那个档里真实 LDM 的结构与真实负载完全不同；**一致性验证通过不等于口径一致**。③ 测试里写死手算常数这次救了我两次：一次抓出方差公式的层间项问题（ρ=0 时块/全批比值落到 1.0119 一侧而不是想当然的 1），一次抓出「MLE 分母会让比值更靠近 1」这个方向完全写反的断言（实际 0.9605→0.9492，离 1 更远）。**仍然开着**：真实模型里同 prompt n 条响应的长度相关性本批没实测（只按「组内接近」建模），这是本轮唯一没有证据支撑的建模假设。
- **并发写入下的收尾纪律（M1 14:08）**：本会话与两个并行会话同时在同一个 checkout 上写 main，收尾阶段连续踩了两个坑，都值得记下来。① **rebase 会把别人的补丁一起重置**：我 `git rebase origin/main` 时，补丁应用阶段把工作区里四份文档的内容覆盖掉，我的 `§13.38` 实验目录、`§0`/`§16`/`§13.32` 注记、readme 索引行全部消失——**`git status` 只显示两个文件有修改**，看上去像只冲突了两处，实际丢了一大片。是逐文件 `grep -c` 核对才发现。补救方式是从原提交 `git show <commit>:<file>` 按文件取回，再用 `diff3 -m` 把「我的改动」三方合并到当前文件，逐段解冲突。② **`--skip` 会连带丢掉对方夹带的另一处改动**：第二次 rebase 时发现 HEAD 已经完整包含我的 `§13.38`（并行会话把我那份一起提交了），于是 `--skip` 跳过重复补丁——但它同时带走了并行会话 `§16 changelog` 的那一行，因为那一行原本夹在我的补丁里。**教训有三条**：收尾前必须按「文件 × 章节」逐项 `grep -c` 核对，不能只看 `git status`；`git add` 要逐个文件确认归属（本轮有一次误把对方整个实验目录加进暂存区，`restore --staged` 撤回）；**为并发写入临时 stash 时记清它属于谁**，别在自己 rebase 完就直接 drop。
- **C 类机制账：收益来源可以分栏，且七个机制没有一个落在同一栏（M1 18:03）**：承接 §18.9 的下一候选「§13.28＋§13.29 合并成第 7 章论点骨架」。两批实验各有一张结论表，却从没放进同一个算式——§13.29 说"省生成量 ≠ 省墙钟"、§13.28 说"删组只再省 3.5%"，两句口径不同，合不成一句话。本轮不重新训练，只读两批归档的 per_seed 重算，把效应分成 L1 生成量／L2 每步成本／L3 到 0.9 步数／L4 墙钟四层，定义 `gap = 1−(1−r)/(1−κ)`。**判决：七个机制无一属"每步兑现型"**——`freq` 每步省 72.3% 而墙钟只省 18.7%（步数 +7.0%，gap −1.93）、`cap` 每步省 0 却墙钟省 6.3%（收益全在收敛）、`cancel` 每步省 1.6% 却墙钟省 34.0%、删组 `C` vs `B` 每步省 44.9% 而到 0.9 墙钟**反而慢 2.7%**。归四类（每步兑现／收敛兑现／双向兑现／被吃掉），7.6 节因此只能写"改了阶段占比与步数、两者方向相反、必须分栏报"。**顺带核出两处正文表述问题**：§13.29 表"到 0.9 墙钟比"列分母混用（`cancel` 记 0.660 是基线/臂，按臂/基线应为 1.515——三格是臂/基线、一格是倒数）；§13.28 ⑤(a)"只再省 3.5%"用的是总成本比之比、分母取相对 `R_nofilter`，配对口径下每步省 44.9%。**教训（两条）**：① **订正别人（哪怕是自己上一批）的数字之前，先怀疑自己的算法**。第一版 `ledger.py` 用"配对均值比分母"配"总量比分母"算 gap，`freq` 得出 −1.947 的怪值；当时第一反应是"归档数据有问题"，实际上是两个比值的分母口径不一致——**怪值先查口径，再查数据**。② **同一张表里出现"比值"与"配对差"两列时，必须断言二者方向自洽**。`cancel` 那一格取倒数后恰好与原符号同号，所以"看起来没问题"；是写成"三种分母都算一遍"的代码才把它揪出来，靠眼看是发现不了的。**仍然开着**：更新成本恒 8 单位是模型假设，"更新吃掉省额"的幅度只是下界；本批只说明收益来源可分离，**不说明哪一类更大**（已明写禁止由此推出"收敛兑现型更值得做"）。

## 00:58 — §13.30 第二批：撤回「跨组排序翻转」这一无效证据，补 verl 组级均衡训练侧锚点

**目的**：复核上一批（00:27 的 §13.30）时发现其核心证据站不住，本批先更正、再补训练侧同栈锚点。

## 01:50 — Rollout 专项：训练侧 mini-batch 组成代价与四框架归约语义核验（§13.32）

目的：接 §13.31 留下的两条残留（训练侧 mini-batch 组成代价、跨框架归约语义），并把结论落进主文档 §13.32。顺序上是**先核语义、再量代价**——如果没有框架改口径，组成就是训练侧剩下唯一可能的代价位置。

## 11:22 — rollout 专项第十批：PrefixGrouper 的微批边界（§13.33）——组在 mini-batch 层被保住、在 micro-batch 层被切掉

目的：推进 rollout 专项在 §20.3.2 必补项之外、M1 权限内可做的那一条残留——「PP 微批边界的影响未量化（`use_prefix_grouper` 下刻意跳过『小微批排两端』）」。该残留由 §13.32 登记，本批（第十批）把它做完，结论写进主文档新增的 §13.34。

做法：先把 verl 快照 `1a9e711e` 的三层切分逐行核清，再照抄进进程内模型，最后用真实 verl 做逐位交叉验证。三层是：① `_balance_batch` 的 prefix_grouper 分支（组级 LDM 后 `batch.reorder`，跳过分区内重排）；② dispatch 把整批按 `DataProto.chunk(dp_size)` 连续切成每 rank 一份；③ 每 rank 上 `make_iterator` 连续切 mini-batch、`rearrange_micro_batches` 按单条长度排名做 LDM（`use_dynamic_bsz_balance` 默认 True，还会把轻的 micro-batch 夹到两端）。

结果（三个判决）：
1. **mini-batch 层组完整性是结构性的**：割点 0.0% 落在组内（60 个组合全零），同一批数据走默认逐条 LDM 则 99.9%。附带发现 dispatch 的连续 chunk 与组级 LDM 分区在 120/120 个组合里逐一相等——靠的是「分区大小 = B/dp」的算术巧合，不是稳健设计。
2. **micro-batch 层完全没有组感知**：默认 16384 预算下 81.3% 的「组-出现」被切开。因为 LDM 按长度排名、`force_group_size` 在本快照没接到 agent 配置，所以「相邻组被按位置切开」的直觉不成立。
3. **折算开销**：每组平均 3.62 段，前缀块开销是整组共享的 3.62 倍（4096 预算时 7.20 倍）；但相对逐条重复仍只有 0.536 倍——PrefixGrouper 收益为正、被吃掉一半多。共享增益恒等于 `1/n`，所以「前缀越长收益越大」不能从本实验推出。

自查修正六处，全部是跑通之后才发现：① 把 `_balance_batch` 的分区直接当 rank 视图（真实 dispatch 是连续 chunk）；② 把 micro-batch 当连续切（真实是按长度排名的 LDM）；③ 组大小与样本长度混用量纲，使 real 口径出现负 FLOP——最危险的一处，若不检查会反向报数；④ 交叉验证用浮点长度，而真实实现用 `attention_mask.sum()`、`torch.arange` 会截断到 0 长度；⑤ 把「前缀越长共享收益越大」当对照，但该比值在本口径恒为 1/n，这条对照必然失败，已换成恒等式与单调性两条；⑥ LDM 复刻的平手比较用 `(w, idx)`、verl 用 `(idx, w)`，已改为同序。

验证范围：22 个单测通过、`--verify` 连跑两次逐字段相同；与真实 verl 的交叉验证 **LDM 120/120、micro-batch 分区 40/40 完全一致**（`xcheck_verl.py`，CPU torch 2.15.0，只跑切分算法、未初始化模型或引擎）。**局限**：进程内仿真、非 GPU 非端到端，墙钟未测；`no_share` 列不是真实默认路径（`use_remove_padding=true` 时同 prompt 的 n 条响应本就只算一次前缀），只能作相对刻度；「片段之间完全不能共享」是上界口径；被跳过的 PP 气泡本身仍未测；长度分布是构造参数。

## 11:45 — rollout 专项第十二批：C3 成对报值的可执行性（§21.7）——近似 η 里有一种恒报 0，同 S 不同 η 的配置只靠成对报才分得开

目的：推进 rollout 专项在 §20.3.2 必补项之外、M1 权限内可做的一项。§21.5 实证了 C2、§21.6 核了 C1／C3 的**可取得性**，但没人验证过：用 §21.6 核出的那些近似口径，C3 自己规定的两个判断（必须成对报 η 与 S、同步基准取 η=0 整步墙钟）还做不做得对。本批把 C3 放进能算出真值的事件图仿真里，结论写进主文档新增 §21.7。

做法：进程内事件图仿真（CPU、仅标准库），30 种子 × 200 步、每批 8 组 × 4 条、组整体失败率 0.25。五个配置——真同步、**流水化同步**（引擎不等训练结束就开下一批，消费的仍是本轮最新批 ⇒ η 恒 0）、两种滞后深度的异步、一种背压（引擎比训练慢一倍、训练侧一半时间在等）。真值 η = 消费时训练版本 − 生成该批所用权重代；三种近似读法只吃引擎侧能看见的量。

结果（五个判决）：
1. **近似 η 的可分性**：训练步版本差与只报最大值都能在 30/30 个种子上判「谁更陈旧」；**只看引擎侧装载版本的一类恒报 0（0/30）**——它不是偏低，而是把「有陈旧」读成「没陈旧」，属方向错。
2. **单独报 S 不可区分**：流水化同步、轻度异步、重度异步三配置 S 逐位相同（23.97，相对差 0）而 η 上限分别是 0／7／19。S 的提升在这里一条轨迹都没多产，全部来自「更新不再串行等待」——这正是 C3 要成对报值的机制，不是一句告诫。
3. **S 的两类偏差方向相反**：分子换成生成侧计数，高报恰好等于 `1/(1−丢弃率)`＝1.335×（与 §21.6 用 SkyRL 每步丢 8/32 组估算的 33.3% 量级一致）；分母剔掉空转，背压配置上修 ×1.667，而无空转的配置反而下修 ×0.833（活跃步分母多摊一段更新墙钟）。靠「偏高还是偏低」分不清是哪一类错。
4. **同步基准选错方向全反**：把另一个异步配置当「η=0 基线」、仍只报生成侧吞吐，真正的同步配置在 30/30 个种子上被读成「比基线慢 16.7%」。本模型里丢弃率与配置无关，故「分子错」只改幅度不改方向（已由测试固定为前提）；真实系统里丢弃率与丢弃机制相关，此时会升级为方向错——这一点本实验**没有**证明，正文已标为未证。
5. **弹性窗口的 η=0 不是 FIFO 的必然**：引擎快 2–5 倍时 FIFO 的 η 反而达 7–31；只有窗口收到 0 才得 η=0，代价是**全部空转**。且 `2 倍／32` 与 `5 倍／32` 的 FIFO max 同为 31（都被窗口顶住）而均值 28.82 vs 30.50、积压深度差一倍——**只报最大值会把两种完全不同的积压读成同一个数**，这是 §21.3 要求报分布的实证理由。

自查修正九处，全部是跑出数之后回头核口径才发现：① 同步配置初版 η 恒为 1，Q1 的判据等于零敏感；② `engine_weight` 读法初版按真值计算，把失效形态掩盖掉了；③ `max_only` 初版是真值换皮（0.0 偏差），根本没模拟「只报一个数」；④ 丢弃率与 η 同源，导致 Q2 没有对照组；⑤ 空转被写成空批步骤，空转率永远量到 0；⑥ **让墙钟读数按假设的 ε 调整——用结论证明结论，速度比当然等于公式**，最严重的一处，已全部撤掉；⑦ `1/(1−丢弃率)` 写成跨种子均值之比（差 2e-4）；⑧ 活跃步分母的推导连错两版；⑨ 弹性窗口的 FIFO／LIFO 对照一度读数全同，被当成「顺序不重要」写进结论，改为扫描积压 × 窗口后才发现顺序确实起作用，同时发现「max 被窗口顶住」这个新读数。其中六处由单元测试抓出，三处由人工核对数值关系发现。

验证范围：16 个单测通过、`--verify` 连跑两次逐字段相同（NaN 按相等处理）；仅标准库、CPU 进程内。**局限**：非 GPU 非端到端，墙钟是任意虚拟秒、不可与论文报值相除；五个配置是构造参数，不代表任何具体系统画像；三种近似是按语义构造、不是从框架源码逐行移植，与 §21.6 的源码核验互为参照、不可互相替代；本实验不支持「某框架报错了 η／S」这类结论。

成果：[实验材料](../experiments/rollout-c3-staleness-identifiability/readme.md)、[主文档 §21.7](../notebook/rollout-performance-research.md)。本批不在 §20.3.2 五条必补项之列，必补项剩余仍为 P-1（多卡窗口，M5 侧）与 P-2（FP8 栈）。

## 12:13 — rollout 专项第十三批：micro-batch 层组完整性的三段归因（§13.35）——3.62× 是相对不可达参照点算的，能接线的上限只有 0.47 倍

目的：推进 rollout 专项在 §20.3.2 必补项之外、M1 权限内可做的一项——§13.34 登记的两条残留：① micro-batch 层 81.3% 的组被切开是否有解；② 被跳过的 PP 气泡能不能补上。动手指的是 §13.34 自己写下的「`force_group_size` 在本快照未接线」，它读起来像「把开关接上就能修」。本批先核源码路径，再量接线能拿回多少、要付什么代价，结论写进主文档新增 §13.35。

做法：先把 verl `1a9e711e` 的 micro-batch 切分与配置注入路径逐行核清，再把 `rearrange_micro_batches` 的三种形态（逐条／组完整／加 vPP）照抄进进程内模型，最后用真实 verl 做逐位交叉验证。

结果（三个判决）：
1. **代码路径**：`force_group_size` 读非张量键、默认 1（`engine/utils.py:71`）；`update_actor` 注入的五个默认键不含它（`engine_workers.py:334-345`）；`ray_trainer.py` 全文零命中；五个训练后端都走没有该形参的 `prepare_micro_batches`；`use_dynamic_bsz_balance` 亦未透传（`transformer_impl.py:650-652`）。所以 §13.34 的条件句「若 `force_group_size > 1`」在引擎入口能核到的训练路径上恒不成立。**残留**：ray trainer 不在该 checkout 的 `enable` 流程里，只核到 engine 入口，不作全局保证。
2. **参照系（最要紧）**：§13.34 的 1.00× 要求「一个 micro-batch 装下整批」，而训练按 mini-batch 迭代，所以这个参照点**不可达**。换成可达上限（每 mini-batch 每组件一次）后：现状 3.69×、上限 1.44×、**能动 0.47 倍**；720 个案例上 `ideal/current` 均值 0.468、区间 0.162–1.000（预算宽松或组数少时收益为零）。「上限 ÷ 外参照」恒等于每个 mini-batch 的组数，与 dp、种子、长度分布无关。
3. **vPP 结构代价**：组完整把批数上限从「样本数」压到「组数」——预算压到 5% 时逐条切给 20 批、组完整仍 8 批。vPP=2 批数比 0.42、不均衡 8.9%→17.0%；vPP=4 比 0.39、11.5%→25.4%；**vPP=3 全部 9/9 触发 `assert num_micro_batches <= num_groups`**（真实 verl 同形态同断言）。方向还随组数翻转：vPP=2 下 `mini_groups=2` 时组完整反而更均匀（0.05% vs 1.59%），`mini_groups=8` 时明显更差（32.3% vs 1.01%）。

自查修正六处，全部是跑通之后才发现：① 三个参照点混用同一个分母，使 §13.34 的 3.62× 被读成落差（最危险，若不发现会把「外参照不可达」写成「有个 bug」）；② vPP 顶破上限时替真实代码 rescale，而真实行为是 `assert`；③ 交叉验证长度上界取 6000，触发 `max_token_len >= max_seq_len` 前置断言，误报「真实不可行」；④ 交叉验证只按异常消息文本分类，而 `assert num_micro_batches <= num_groups` 没有消息；⑤ 识别性检验只用 `details[0]`（仅 `mini_groups=2`）代表整层，漏掉 vPP=4 的失败案例；⑥ 单测期望值先写成「比值 = 一个 mini-batch 的组数」，而分母是整条 rank 视图的 `B/dp/n`。

验证范围：15 个单测通过、`--verify` 连跑两次逐字段相同；与真实 verl 交叉验证 8 个形态——7 个可切形态分区 7/7 完全一致，1 个形态两侧同判不可行（`xcheck_verl.py`，CPU torch 2.15.0，只跑切分算法、未初始化模型或引擎）。**局限**：进程内切分形状复刻，非 GPU 非端到端，所有倍数都是**前缀块 FLOP 比值**、墙钟未测；可达上限沿用 §13.34 的上界假设（碎片之间不共享），故 0.47 倍应视为**收益上限**；不计 PP 气泡，故不能说「接线一定亏」；长度分布是构造参数。

成果：[实验材料](../experiments/rollout-microbatch-group-integrity/readme.md)、[主文档 §13.35](../notebook/rollout-performance-research.md)（另更新 §0 最近更新、§13.1 可比性能行、§13.34 的残留注记、§16 changelog）。本项不在 §20.3.2 必补项之列，必补项剩余仍为 P-1（多卡窗口，M5 侧）与 P-2（FP8 栈）。

## 13:10 — rollout 专项第十四批：force_group_size 有没有生产者（§13.37）——§13.35 的残留可以整条划掉，0.47 倍是「有人写生产者」的上限
目的：收掉 §13.35 判决一留下的那条残留——原文写「`force_group_size` 的接线在 ray trainer 侧，而 ray trainer 不在该 checkout 的 `enable` 流程里，本批只核到 engine 入口为止，不作全局保证」。这句话读起来像「可能还有一条没核到的路径把开关打开了」。本批不去核那条路径，而是检验一个更强的命题：**整个 checkout 的非测试代码里根本没有写入方**。结论写进主文档新增 §13.37。
做法：静态读源码，不执行 verl。先全仓扫 `assign_non_tensor(_data)?` 且键名为 `force_group_size` 的三种写法（位置参数、`key="..."` 关键字、直接 kwargs）；再把三条「看起来可能写入」的旁路逐条读掉（默认键注入、TransferQueue 回写、配置层）；最后读引入史，弄清为什么会漏成「功能在、没人喂」。
结果（三个判决）：
1. **写入方计数：生产代码 0 处，测试 1 处**。唯一写入方是 `tests/utils/test_prepare_micro_batches_with_group_size.py:64`，它构造假输入——这个特性目前唯一的使用者是它自己的单元测试。`docs/`／`recipe/`／`examples/` 零引用。
2. **三条旁路逐条排除**：① `train_batch`（`engine_workers.py:335`）、`infer_batch`（`:389`）、tinker（`engine_workers_tinker.py:134`）三处 `default_keys` 都是静态字面量，五个键都不含它；② TransferQueue 回写确实是唯一能把键带进后续 batch 的通道——`@register` 对所有方法都套了 `tqbridge`（`decorator.py:425`），输出里的 `NonTensorData` 会被塞进 `extra_info` 再回注（`transferqueue_utils.py:135-152` 与 `111-132`）——**但 `train_mini_batch` 只回 `metrics`（`engine_workers.py:315-320`），键根本不进输出，通道断在源头**；③ `EngineConfig`（`config/engine.py:77-107`）没有该字段，用户在 yaml 里无处可配。

## 13:56 — rollout 专项第十五批：mini-batch 组成基准的估计偏差（§13.38）——1.0508 应读成 1.0462，分子分母块结构不同

目的：收掉 §13.32 留下的那句残留——「组内连续排列作为基准含『组内样本相邻 → 方差被低估』的估计偏差，组成效应的精确量级依赖该偏差的修正」。这句话里有三个独立问题一个都没答：偏差方向是什么、量级多大、以及 §13.32 论证「真实 LDM ≈ 交错」用的「长度与 uid 无关」构造分布在真实 GRPO 里成不成立。结论写进主文档新增 §13.38。

做法：先只读核对真实数据顺序（三条 anchor 在 verl `1a9e711e` 全部命中）：`ray_trainer.py` 的 `batch.repeat(repeat_times=n, interleave=True)`（同组连续排列）、`actor.yaml:122` 的 `shuffle: false`（mini-batch 是连续切片）、`seqlen_balancing.py` 的 `karmarkar_karp`。然后把同一批样本梯度放进三种块组成里比较（真实 LDM 重排后连续切／组内连续排列／严格交错），并用真实 LDM 复刻件（§13.30／§13.31 的实现，本批用 `ast` 抽出真实 `karmarkar_karp` 在沙箱跑 120 例逐位核对）驱动长度相关的四档长度结构（iid／realistic／strong_corr／degenerate）。

结果（三个判决）：
1. **偏差方向随组信号强度 ρ 翻转，不是无条件「偏小」**。两层结构的无偏样本方差期望是 `E[s²] = [(1−ρ)·m·(n−1) + ρ·n·(m−1)] / (m·n − 1)`；8 组/块 ÷ 32 组/块的比值 ρ=0 时 **1.0119（基准反而读大）**、ρ=0.5 时 0.9605、ρ=1 时 0.9140，**交叉点 ρ≈0.12**。默认 ρ=0.5 落在偏小一侧，结论成立但是**带条件的**。解析值 0.9605 与直接实测（同一批样本按组连续切 4 块）的 **0.9578** 一致。
2. **1.0508 的分子分母不是同一种块结构（本批最要紧的一处）**。长度全同时，`grouped`（分母）每块装 **8 个完整组**，而真实 LDM（分子）每块装齐 **32 个组、0 个完整组、每组跨 4 块**——权重全等时 LDM 堆状态完全对称，等分入堆后分区下标是 `(0,4,8,…)/(1,5,9,…)`。所以 1.0508 这个比值两侧块结构不同：**基准偏差 4.12%（占 81%）、真实组成效应只值 0.93%（占 19%）**。换到真实长度结构（同 prompt 的 n 条响应长度相关，LDM 把同组摊开、块内 **29.8/32** 个组），读数是 **1.0462**，其中 **98% 是真实组成效应**——这恰好把 §13.32「真实路径已接近最坏组成」的定性判断变成定量版本，也说明 1.0508 与 1.0462 的 0.44% 差是**口径差不是噪声**。
3. **「交错排列是上界」只在平均意义成立**。`interleaved ÷ ldm` 四档均值 1.0050／1.0045／1.0035／1.0000，但逐种子最低落在 **0.9972–0.9992**，真实结构下只有 **90%** 的种子 ≥1。§13.32 在长度全同的对照档里得到恰好的 1.0000（交错与 LDM 逐位同构），据此说「真实路径 ≈ 最坏组成」；真实长度下这个结论不再精确成立。

自查修正三处，全部是跑通之后才发现的：① **「长度全同 ⇒ 每块 8 个完整组」是错的**——真实 LDM 在权重全等时把 32 个组摊到全部 4 块，这条错误让第一版分解把「基准偏差占大头」错算成「真实组成效应占大头」，方向读反；② **偏差方向被写成无条件的「基准把方差压低」**——ρ=0 时实际是抬高（1.0119），已按 8 组/块参照写出交叉点并把「默认 ρ=0.5 落在偏小一侧」写进结论条件；③ **MLE 分母的方向与原预期相反**——原以为除以 N 会让比值更靠近 1，实际 0.9605→0.9492 **离 1 更远**（分母变小对 N=64 的分子相对影响比对 N=256 的分母更大）。另有两条初版测试断言方向写反（「组内越相关 ⇒ 组越散」应为「组越聚」；识别性判据在测试里另起一套规则而实现里有自己的判定），都由测试自己抓出后改成同一规则。

识别性检验的一处细节：两条指标量级差三个数量级，判据必须分开。`ldm/grouped` 用普通相对极差（8.0% 敏感）；`interleaved/ldm` 读数在 1.0006–1.0078 之间，必须用「离 1 的偏移」的极差（92% 敏感）——用普通相对极差只有 0.72% 会把一条真实敏感的指标判成不敏感，直接用 `max|v−1|` 又会把「恒比 1 大一点点但不动」的无效指标判成敏感。两种错法都写成测试。两个负向对照（恒常数、与 ρ 无关的组跨度几何量）均判零敏感。

## 13:58 — PP 微批边界成本：被跳过的「小块排两端」在 max 模型下是负优化（§13.39）

### 目标

### 做了什么

先读源码把可比性钉死，再建模型算。四个事实：`global_idx = [j for partition in lst for j in partition]` 使 partition 顺序 = rank 内顺序（`ray_trainer.py:1244`），dispatch 用 `chunk(dp_size)` 连续等分（`decorator.py:71-88`），rank 内再按 `mini_batch_size_per_gpu` 连续切成 micro-batch（`engine_workers.py:295-309`）。因此"跳过重排"只改 rank 内顺序、成员集合不变。

### 结果

- **`max` 模型下这段重排是负优化**：`cur`/`sorted` 36 格全不优于，区间 1.0000–1.6462（均值 1.2064）；`plain` 更差（最差 2.5105）。

## 14:41 — C3 的同步化基准不可从 trace 内取：trace 内的 η=0 步只是冷启动（§21.8）

### 目标

接 §21.7 剩下那一半：§21.7 只实证了 C3 第一半（η／S 各自能分辨什么），而 C3 还有一条从未被检验的规定——**"同步化基准取同栈 η=0 整步墙钟"**。本轮只问一件事：**这个基准能不能从一条 async trace 里读出来？**

### 做了什么

改用**因果记账**建事件驱动仿真：版本只在 update **完成**时推进，批的权重代 = 开始生成时读到的版本。K 个副本、每副本每 T 产出一条完整批、每次 update 耗时 U。与 §21.7 的两处差异即本轮论点：① 因果记账下"流水化同步"不是 η=0；② 暂停与否则只在生成受限（U<T/K）时有墙钟差。

### 结果

- **判决一（结构性）**：拿「trace 里 η=0 的步」当基准，16 格配置（K=1/2/4/8 × U/T=0.1/0.3/0.7/2.0）的 async 收益**全部读成 1.000×**，真实是 1.099–8.527×。三件事同时成立：定义集 100% 来自第 0 步（`n_eta0_later` 全 0）、该值恒 `T+U` 与 K 无关、同一估计量用在暂停同步 trace 上精确（差 0.0000）。丢掉 trace 第一步后 30/30 种子无定义。
- **判决二（替代估计量的边界）**：「到达计数＋无等待步」合成 `T+U` 在 K=4 主要区间 +0.4%～+1.6%；K=1 确定性下 `no_wait_frac=0`、Û 结构性无定义。短 trace 偏差严格 = `K/steps`（20 步 +12.8%、50 步 +5.1%、200 步 +1.3%）。两条负向对照：最小墙钟当 U 在 U 有抖动时低估（1.05–1.11 对 1.10）；到达间隔中位数估 T 退化到 0.1（副本同步启动）或仍偏低——**中位数不是速率**。
- **判决三（η 不够用）**：K=1 时暂停同步与流水同步的 η 逐位相同（1.000），墙钟差 0.0995／0.4975／0.9950（=`U·(1−1/steps)`）；K=4 时降到 0.0245→0→0。差只在生成受限时出现；U≥T/K 时暂停**只是版本绑定的语义选择、不是性能选择**。
- **判决四（窗口造 η=0 的代价）**：窗口收到 0 能让 trace 处处 η=0，但丢弃率 46.7%、吞吐 0.65×（比同步还慢）、估计量仍偏 +53.6%。

### 自查修正（五处，均跑通后发现）

1. **版本重复推进**：初版在消费与 update 完成各加一次，K=1 周期变成 8T、速度比全 <1。
2. **事件顺序**：paused 形态的副本在 update 开始前就被重启（同一时刻事件序），两种形态读数一度完全相同。
3. **gap 解析式猜错两次**：先猜 `min(T/K,U)`、再按 `T−U` 写测试，实测是 `U·(1−1/steps)`。
4. **`warmup` 开关是死代码**：预设的"稳态起点"全部 1e-9 量级，永远走不到；删掉后改为「丢弃前 R 步」的读法选择。
5. 两处测试用 `assertEqual` 比较 0.3 与 0.30000000000000004。

### 结果

| 批大小 | 逐条 | 组级 | 代价 |
|---|---|---|---|
| 256 | 1.0263 | 1.0942 | **+6.61%** |

| 4096 | 1.0032 | 1.0051 | +0.18% |
| 16384 | 1.0010 | 1.0012 | +0.02% |

## 18:03 — C 类机制账：省下的每步成本有多少被吃掉（§13.42，落地 §18.9 下一候选）

**目的**：把 §13.28／§13.29 两批结论放进同一个算式，给出 §18.9 第 7 章 7.6 节的论点骨架。两批各说各的口径（"省生成量 ≠ 省墙钟"、"删组只再省 3.5%"），合不成一句话。

**结论**：2 卡的「gen 二态」（4.17s vs 2.15s）不是生成或副本调度现象，是 V1 sync trainer 的 2.0s 采样轮询取整。逐请求计时 30 步：29 个干净训练轮**全部 64/64** 分到两个副本、派发窗 ≤0.09s、整轮生成跨度 1.49–2.26s——没有任何慢轮；`timing_s/gen` 的慢态多出的 2.01s 全在 `replay_buffer.sample` 等待（4.045 vs 2.033s），`sleep` 两态都 0.12s。慢/快按「生成跨度是否越过 2.0s」**15/15 完全分离**。

## 19:06 — 订正 §13.43 的派生量 gap：它不是收敛代价（第二十四批）

**目的**：补做同日第二十三批立账时漏掉的**强制恒等式核对**（当时用派生缺口 `gap` 回答"省下的每步成本有多少被吃掉"，并据其符号给四个机制下了机理判词）。不跑新实验。

**结论**：`1−r ≡ wall_ratio`、`1−kappa ≡ cost_ratio`，故 **`gap ≡ 1 − wall_ratio/cost_ratio`，步数被完全约掉**——"`gap<0` ⇒ 收敛变快／`gap=1` ⇒ 全部被吃掉"两条读法作废。两条反例都出自本材料：`freq` gap **−1.93** 而 `steps_ratio` **1.070（变慢）**；`C` vs `B` gap **1.0** 而 `steps_ratio` **0.965（变快）**。由此抓出 `cap` 误判——初版"墙钟省 6.3% 全来自收敛"，补 `traj_ratio` 后是 **0.282**，实为**省样本**；`cancel` 的"收益全在收敛"不成立（轨迹 0.984，机制在每轮固定成本，分项未定）。四类改按 `cost_ratio`／`traj_ratio`／`wall_ratio` 直接读数归类。**G2 撤回"`gap` 是收敛代价的度量"**，改为需四字段同报、语料内齐全者为零。
