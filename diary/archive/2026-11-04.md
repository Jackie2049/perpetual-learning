## 05:04 — 审 band_floor 三档判据：补掉自记的边界缺口，抓出一处「同口径」其实不同口径

**目的**：接第十一批自己写的「留给下一轮」①——`band_floor.py` 的三档判据只跑通、没审过。本轮只审这一层，不新开实验、不改任何测量值。

**一、判据本身成立，但有一处名不副实。** 第十一批 readme 写 `band_floor` 与 `fifo_reorder_band` 用"同一 rng 种子、同一 shuffle 序列"。核对源码：两边都写死 `s * 7919 + t`，**不含 `rng_seed`**，且 `band_floor.py` 与 `real_lengths_policy.py` 各写一份。在 `rng_seed=0`（当前全部调用）时恰好等价，换成任何非零种子就会**静默错位**——错的不是读数，是"两处同一抽样"这个保证。已统一为 `rng_seed * 100003 + s * 7919 + t` 并在两处注明"改一处就一起改"。

**二、`band_floor.py` 改为不自己算一份。** 第十一批的脚本自带一份逐种子分解、并声称与归档同口径，实际上是"两份实现刚好相同"。现在它直接调 `RL.fifo_band_floor` 取归档用的那个值，自算的分解只用于**交叉核对**（新增 `crosscheck` 字段），不一致时退出码 1。16 格 **crosscheck 全 ok**，与 `real-lengths-summary.json` 的 `band_floor` 逐格一致，分布 `usable` 13／`no_reading` 2／`degenerate` 1。

**三、补掉第十一批自记的边界缺口。** 它当时记下"把 `>` 改成 `>=` 时 5 条测试全绿"，并写"恰为一半（15/30）的输入没有专门测试"。本轮用搜索构造出一个**恰好落在边界上的输入**：40 组里 33 组贴顶，30 个抽样种子里正好 15 个抽到全贴顶的 16 组 ⇒ 15/30。新增两条：
- `test_exactly_half_zero_band_is_still_usable`（15/30 ⇒ `usable`，默认"过半"是**严格多于一半**）；
- `test_one_more_zero_band_flips_to_degenerate`（34 组贴顶 ⇒ 18/30 ⇒ `degenerate`）。

两侧各注入一次：`>`→`>=` 时前一条红，`* 2 >`→`+ 1 >` 时后一条红。⇒ 原先"5 条全绿"的那个缺陷现在两侧都被钉住，不再只是靠 15/30 与 30/30 从两侧夹住。

**四、归档同步核对。** 改了 shuffle 种子式子后重算 `real-lengths-summary.json`：旧字段 **673 个 0 变化 0 删除**，新增 48（16 格 × 3 键）；`real_lengths_policy.py --verify` 逐字段相同；`bucketing_probe.py` 重跑输出与归档一致。`band-floor.json` 不入库（`band_floor.py --json` 的产物，含 crosscheck，可用一条命令重生成）。
