第 0 章：自行讲解 —— DeepInfer 到底是什么

0.1 一句话定义

DeepInfer 是 DeepSeek 把自己跑 V4.1-Flash 大规模生产推理服务的那个「引擎本体」开源了出来——但它不是"完整服务"，而是"可扩展的推理内核"。

关键认知：DeepSeek 之前开源的 FlashMLA / DeepEP / DeepGEMM / TileLang 都是"零件"（算子库）。DeepInfer 是第一次把这些零件组装成一个完整可跑的推理引擎——调度、KV、采样、推测解码、负载均衡全部耦合在一起。但它刻意没有开源全服务：KV cache 系统、VE/Prefill/Decode 分离、跨 DP 副本负载均衡这三块因与内部基础设施耦合太深，留在内部（README 明说，知乎 Blog 讲设计）。

0.2 它真正解决的三件事（生产视角）

  • 让自家模型跑得比别人快——深度绑定 V4.1-Flash 架构（压缩注意力、SWA、MoE、MTP），把模型特殊性榨到极致。它是"模型专用 + 深度优化"，不是通用框架。
  • 多芯片——同时支持 NVIDIA SM100 和华为 Ascend 950。这在中国 AI 生态是刚需（卡荒 + 国产化），DeepSeek 是第一个"模型厂商官方、直接支持昇腾"的推理框架。
  • 低成本高吞吐——单集群 155 万亿 tokens/天、每卡每小时 38 美金（谷价）。推理框架最终拼的是"每卡每小时产出多少价值"。

0.3 我的本质判断

与其说 DeepInfer 是"又一个 vLLM 竞品"，不如说是 DeepSeek 把自家模型的"正确推理实现"公开化。它给了三个信号：

  • 对使用者 要私有化部署 V4.1-Flash，DeepInfer 是"官方正确路径"，不是社区适配。
  • 对研究者 ZOS、DSpark 变长、V4 混合注意力一体化元数据，是真正的系统论文级创新，值得单独深挖。
  • 对生态 DeepSeek 从"给模型"到"给模型+配套推理引擎"，把"DeepSeek 栈"闭环了。

本报告主线即按此理解展开："模型厂商专用推理引擎的完整技术剖析"，不是泛泛的框架对比。

0.4 Take Away —— 可迁移的核心知识点

以下是从 DeepInfer 里提炼的通用洞见，即使忘掉这个项目和报告本身，也依然有用：

① 吞吐的天花板在"调度-执行重叠"，不在单算子

ZOS 的本质不是某个 kernel 快，而是让 CPU 调度完全被 GPU 计算掩盖。对任何推理/训练引擎，把"决策"和"执行"解耦重叠，往往比优化单个算子的收益更大。这是"系统优化"和"kernel 优化"的分水岭。

② 推测解码应从"启发式"升级为"在线优化"

固定的 speculative length 是拍脑袋。DeepInfer 把它变成每步在线解一个最大化问题（吞吐 = 期望接受 token / 估计耗时），用运行时实测的耗时模型动态调 batch 和 draft 数。任何有代价的"投机"决策，都可以套用"在线目标优化"的思路。

③ "模型专用"和"通用框架"是两种值得并存的设计哲学

通用框架（vLLM/SGLang）靠生态广度赢；模型专用引擎（DeepInfer）靠把模型特殊性榨到极致赢。判断一个系统时，先分清它是"适配所有模型"还是"为一个模型量身定做"——两者的优化目标和评判标准完全不同。

④ "预编译数据搬运计划"比"运行时逐个查表"更高效

块加载计划（block_load_plan）把 KV 的 scatter/gather 预先编码成一段表（[src_block, begin, end, dst]），运行时一次拷贝完成。凡是"同一类搬运反复发生"的场景，都值得先做编译/规划，把运行时的工作变成查一条指令。

⑤ 确定性和"batch-invariant"是多层约束，不是单个开关

DeepInfer 的确定性跨 kernel（确定性算法）、通信（限制归约路径）、采样（位置哈希 RNG）三层。判断一个系统是否"可复现"，不能只看有没有固定随机种子，要看它是否把确定性当跨层不变量在设计。

⑥ 运行时负载均衡，不应打断前向执行

EPLB 在权重 shuffle 时用对称内存镜像/NCCL P2P，使"重排专家"不打断模型前向。任何需要运行时重分配资源的系统，"热重排而不停机"都是关键工程指标。

⑦ 开源贡献的采纳规律：公司内部驱动 vs 社区驱动

DeepSeek 生态是"公司内部批量 release"式维护，外部 PR 周期长（FlashMLA open PR 平均 185 天）；verl/vLLM/AReaL 是社区驱动、外部 PR 采纳高。选贡献目标时，先判断项目是"公司护城河"还是"公共设施"——后者对个人贡献者友好得多。

第 1 章：项目说明

1.1 背景与动机

  • DeepSeek 从 V3/R1 起就自研推理系统（DualPipe、DeepEP、EPLB 都服务于它）。
  • 先开源零件（算子库），再开源引擎（DeepInfer），最后开源配套（deepseek-recipe token 编解码）。
  • 动机：①给 V4.1-Flash 私有化部署一个"官方正确实现"；②生态卡位（多芯片 + 国产化）；③技术展示（155 万亿 tokens/天 的工程实力）。

1.2 目标与定位

  • 目标：单集群最大吞吐、最低延迟，多芯片可移植。
  • 定位：模型专用的高吞吐推理引擎，非通用服务（开源版明确缺 KV / PD 分离 / 负载均衡）。

1.3 软硬件要求

维度要求
软件Linux、GCC ≥ 13、Python 3.12、CUDA 13（NVIDIA）/ CANN 9.2（Ascend）
硬件NVIDIA SM100（Blackwell）、华为 Ascend 950
关键依赖torch 2.13、tilelang、xgrammar、自家 kernel 库（vendor submodule）
支持模型DeepSeek-V4.1-Flash（默认 checkpoint 1017）

1.5 与自家算子库的分工

  • FlashMLA：MLA 注意力本身（flash_mla_sparse_fwd / flash_mla_with_kvcache / fused_norm_rope_attn_rope_cast）。
  • DeepGEMM：FP8/FP4 GEMM（bf16_gemm_nt、fp8_einsum）。
  • DeepSelect：topk（sampler 取 top-k、候选块选择）。
  • tilelang_ops：自研内核补三者未覆盖且与自家模型强耦合的算子（压缩 KV、YoCo、DFlash、engram、HC）。

第 3 章：核心方法

3.1 ZOS（Zero-Overhead Scheduling）零开销调度

问题：推理中 CPU 调度和 GPU 计算是串行的，GPU 常等调度器。

解法：decode 的 post-process 延迟一个 step，与下一步 forward 在 GPU 上重叠（worker.py:182-187），让调度器 CPU 开销被 GPU 计算完全掩盖。

难点与解法：在途 seq 可能被抢占重算 + varlen 下 seqlen_q 需按上一步采样结果修正，导致 CPU 元数据滞后一步。_correct_seqlens_qk（worker.py:191）用 prepare_zos_inputs（zos.cpp:142）算 remap（本步与上步 batch 的 seq 对应关系），GPU 上用上一步 confidence rates 修正 seqlens_q/k，D2H 回读刷新采样元数据。

token 打包优化（zos.cpp:31）：无重叠时打包最终 input_ids；有重叠时只填 fresh rows，matched rows 复用上一步 GPU 输出，减少 H2D 拷贝。

decode step N:  Forward ──► post-process(上一步) ──► Sample ──► post-process(当前步, 存入 prev_step)
                                  │
decode step N+1: Forward ─────────┘  ← 上一步 post-process 与这里重叠

3.2 DSpark / MTP 变长自适应推测解码

不是固定 speculative length。Scheduler 先选定请求；MTPVarlen.schedule（mtp_varlen.hpp:150）再动态选择验证 token 总预算 total_q 和每请求验证长度，不增删请求。best_bsz 不是请求数；最大化的是 估计接受 token / 估计耗时 代理目标，不是实测吞吐保证。

  • 耗时估计自适应：ForwardRuntimeEstimator 用双层中位数滑动窗口动态拟合 slope_ms = (forward_ms - baseline) / graph_size；运行时由 engine 用 CUDA event 实测喂入持续校正。
  • 接受率：MTP confidence head 逐位累乘（process_MTPInfo），N-2 轮算 best_bsz、N-1 轮贪心分配每请求 seqlen_q。
  • DFlash 深度集成：draft 特征随主模型 CUDA graph 捕获写入 main KV cache；MTPInfoPool 跨 step 稳定存储。

价值：推测解码从"启发式"变成"在线优化问题"。

3.3 V4 混合注意力一体化元数据

dense 压缩层 + sparse（top-k 索引注意力）+ SWA + YoCo + engram，全在调度阶段生成块加载计划（block_load_plan.cpp 的段表 [src_block_id, src_begin, src_end, dst_offset]），把多层不同注意力的 KV 加载统一成一次 GPU 拷贝指令。

价值：把"scatter/gather KV 加载"变成预编译的加载指令，减少内核发射。

3.4 YoCo Bounded Replay

  • 模型切成 prefill 半区 + consumer 半区，consumer 层 SWA 有界截断，减少 decoder prefill。
  • compact 模式（真截行 + CP 重分布）/ mask 模式（只收窄可见域 pivots）双模式。
  • 约束：keep_tokens ≥ window_size + max_backtracking_tokens。

3.5 EPLB 运行时热重排

  • 冗余 expert 动态分配（贪心"加副本后最大每副本负载最小"）+ 贪心跨 rank 排布。
  • 运行时 inplace 权重重排：NCCL batched P2P 或 symm_mem IPC 镜像（免通信），权重 shuffle 不影响前向执行。

3.6 确定性采样 + batch-invariant

  • RNG 用 seq_seeds + 位置 hash（DRAFT_POS_HASH_MUL）+ tag（"default"/"mtp"）分隔命名空间。
  • 官方确定性支持条件为 batch-invariant 模式、固定请求 seed，并关闭变长 MTP 验证（ENABLE_MTP_VARLEN=0，仅 NVIDIA）；不能只靠固定 seed 或 batch-invariant 单项开关保证完整自由采样结果一致。本报告未进行端到端实测。
  • 结构化输出（regex/JSON/EBNF）由 xgrammar 编译、bitmask 异步 pinned 拷贝、MTP 下逐 draft 独立 mask。

第 4 章：系统架构

4.1 系统分层（宏观）

LLM (entrypoints/llm.py, vLLM 风格 offline batch API)
 └─ LLMEngine (engine/llm_engine.py) — Python 编排
    ├─ Scheduler (csrc/engine/scheduler.hpp) — C++ 调度核心（GIL 释放）
    ├─ BlockManager / state_manager — KV/状态块管理
    ├─ MTPVarlen — DSpark 变长推测分配
    ├─ Sequence — 序列状态机
    └─ Worker (worker/worker.py) — 每步 Forward→PostProcess→Sample→PostProcess
        └─ ModelRunner → DeepseekForCausalLM
            ├─ DeepseekDecoderLayer × n（MLA / SWA / MoE）
            ├─ DFlash（MTP 投机模块）
            ├─ Sampler（确定性 + 结构化输出）
            └─ EPLB（ExpertLoadBalancer）

4.2 核心模块中观架构

  • Scheduler：三队列（waiting/prompted/running）、三种 EngineType（NORMAL/PROMPT/COMPLETION）、BlockManager、MTPVarlen。NORMAL 用 DP 组 ALL/ANY 双投票点 + 两轮 allreduce 统一 prefill/decode 步型。
  • Worker：统一 prompt/decode/placeholder/ZOS 四类步型，走同一个 Forward-PostProcess-Sample 循环。
  • ModelExecutor：FP4/FP8 混合量化加载、FlashMLA 薄封装、采样器、EPLB、tilelang_ops 分发器（cuda/asc 双后端工厂）。
  • 分布式：shm_broadcast（无锁共享内存广播）+ 并行组拓扑（World/DP/CP/EP/Engram）。

4.3 与上下游组件关系

  • 上游：HF 权重（V4.1-Flash）、请求 API（vLLM 风格）。
  • 下游：FlashMLA / DeepEP / DeepGEMM / DeepSelect / TileLang kernel、vendor submodule。
  • 未开源边界：KV cache 系统、PD 分离、负载均衡（EngineType 三态 + shm_broadcast + profile_server 已为这些铺垫）。

第 5 章：硬件后端 —— GPU / NPU 双后端与解耦设计

5.1 平台抽象

platform.py 定义 PlatformEnum(GPU/NPU) + 抽象基类，统一暴露：tilelang_ops_backend、distributed_backend、fp8_sf_type、pin_host_memory、get_distributed_options。运行时按硬件探测（DEEPINFER_ACCELERATOR 只是 build 开关）。

5.2 NVIDIA（SM100 Blackwell）特化

  • tilelang_ops_backend=cuda、distributed_backend=nccl、fp8_sf_type=int32。
  • NCCL 配置 max/min_ctas = DEEPINFER_NCCL_NUM_SMS（默认 32）。
  • 独有：DEEPINFER_BATCH_INVARIANT 与确定性采样（仅 NVIDIA）。

5.3 Ascend（950）特化

  • tilelang_ops_backend=asc、distributed_backend=hccl、fp8_sf_type=int16（NPU 用 FP8 scale 是 int16，GPU 是 int32）。
  • torch_npu.transfer_to_npu 映射 cuda→npu；npu_ops/patch_imports.py import hook 把不支持的 CUDA 算子懒重定向到 NPU 实现（DeepSelect topk 回退 torch、ViT 走 npu_fusion_attention）。
  • 一大套环境补丁：PYTORCH_NPU_ALLOC_CONF、TASK_QUEUE_ENABLE=0、HCCL 超时参数等。

5.4 后端解耦设计

  • csrc WITH_NPU 宏：get_default_device()（kPrivateUse1 vs kCUDA）、make_from_blob()（NPU 走 at_npu::from_blob）。
  • tilelang_ops 双后端工厂：ops.py 按 tilelang_ops_backend 动态 import cuda/ 或 asc/ 包，收集所有 xxx_tl 工厂 re-export。
  • 硬件探测中立层：deep_cluster/hardware/device.py 纯硬件中立，向上只暴露 accelerator 无关接口。
对 Ascend 生态的意义：DeepInfer 是首个"模型厂商官方 + 双后端（含昇腾）"的推理框架。NPU 被当作一等公民完整支持（HF 加载、HCCL 并行、IPC、profile、MoE/MTP/Engram/YoCo 全部 NPU 可用），但有降级点：sampler 的 DeepSelect topk 未就绪、ViT flash_attn 走 npu_fusion_attention、batch-invariant 仅 NVIDIA。

第 6 章：结论与展望

6.1 结论

  • DeepInfer 是"模型厂商专用推理引擎"的代表作，三大创新机制（ZOS / 变长 MTP / V4 一体化元数据）值得研究。
  • 双后端（SM100 + Ascend 950）是生态卡位，尤其对国产化意义重大。
  • 深度绑定 V4.1-Flash，把模型特殊性榨到极致——这是它相对 vLLM/SGLang 的本质差异。

6.2 对研究的启示

  • ZOS / 变长 MTP 有系统论文潜力。
  • batch-invariant / 确定性采样 的实现链可迁移到 vLLM / verl（这正是我们一路深挖的主题）。
  • V4 混合注意力 + YoCo 是 DeepSeek 对长上下文 + 高吞吐的新解法，无直接对照。

6.3 对 perpetual-learning 的意义

  • 可深挖的技术点：ZOS 调度、变长 MTP、EPLB 热重排、确定性采样链。
  • 可借鉴的实现：块加载计划段表、cudagraph buffer 复用、对象池 + DeferredRelease。
  • NPU 方向对照：与 vLLM-Ascend / MindIE / Ascend 生态系列对照。

6.4 局限与后续

  • 只支持 V4.1-Flash，非通用；CUDA 13 / CANN 9.2 门槛高；当前 Darwin 仅做源码/CPU。
  • 未开源部分（KV cache / PD 分离 / 负载均衡）可能后续开放，值得跟踪。
  • DeepSeek 承诺"未来新模型的推理代码及优化将在 DeepInfer 中持续开源"——生态会持续演进。
本报告基于对 DeepInfer 源码（浅克隆 8b161497）的三路并行精读（调度器/引擎、模型执行器、NPU/分布式/入口）+ 官方部署 Q&A + 配置/依赖核验。技术结论为源码静态分析，未在目标硬件实测。
